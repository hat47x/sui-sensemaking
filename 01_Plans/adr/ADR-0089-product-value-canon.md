# ADR-0089: プロダクト価値の正本と、価値をADRへ反映する規則

- Status: Accepted
- Date: 2026-10-01
- Deciders: Maintainer
- Scope: `01_Plans/adr/`, `ROADMAP.md`, `README.md`
- Supersedes: 価値の「現在の定義」に関する `ADR-0001`・`ADR-0011`・`ADR-0036`・`ADR-0037`・`ADR-0038`・`ADR-0042` の運用部分（原則・不変条件・モデルそのものは `ADR-0010`・`ADR-0032`・`ADR-0041` が引き続き正本）

## Context

プロダクト価値が ADR-0001/0010/0011/0032/0036/0037/0038/0041/0042 などへ分散し、一次利用仕事と切替理由は削除済みの issue（`PRODUCT-POSITION-01`）にしか書かれていなかった。管理文書の整理（2026-10-01）で issue 台帳を廃止したため、価値の現在地を1か所で読める正本が必要になった。あわせて、ADR が価値へどう寄与するかを毎回確認する規則がなく、運用系のADR（フェーズ計画、文書運用、認証的なガバナンス）が価値判断と混ざっていた。

開発体制は **1人の開発者＋生成AI** である。外部協力者や複数人承認を前提にした検証・統治は置かない。

## Decision

### 1. 一次利用仕事

> まとまりきらない定性資料や観察を、早すぎる分類・要約・合意で潰さず、出典・異論・保留・人間の判断権を残したまま構造化し、後から根拠へ戻れる共有可能な理解へ育てる。

### 2. 切替理由

次のどれかが既存手段で痛みになったときに選ばれる。

- 付箋/ホワイトボード: なぜその束・結論になったかを後から根拠へ戻りにくい。
- 一般的なAI要約/クラスタリング: 少数意見・違和感・保留が、きれいな結論へ吸収されやすい。
- 質的分析ツール: コード体系や分析者の枠を先に強く持ち込みたくない探索初期に合わない。
- 文書/スプレッドシート: 距離・配置・関係・空白を使った構造発見が弱い。
- クラウド前提の共同ツール: 機微な定性資料を local-first / offline で扱いにくい。

### 3. 競わない軸

最速の自動要約、自動での正解・合意・意思決定、汎用ホワイトボードの機能数、定量・統計解析、人間のレビューを省くAIエージェント化。

### 4. 価値の構成（既存ADRへの索引）

| 層 | 内容 | 正本 |
|---|---|---|
| 価値原則 P-01〜P-09 | 意味の保留、反スコアリング、人間レビューの追跡、HITL反復、カード数の可管理性、視点制御、self-host/privacy、定性情報への忠実性、累積的探究 | `ADR-0010`（詳細は `ADR-0001` §1） |
| 価値ループ V0〜V4 | 開始 → 外在化 → 構造化 → レビュー → 共有と学習 | `ADR-0032` |
| 非後退不変条件 CVI | SafeMode既定ON、proposal-only、人手レビュー昇格のみ、Consensus直接更新禁止、dryRun無副作用、provider=noneで価値成立、保留・違和感の非破壊 | `ADR-0041` |
| 累積的探究 | W型反復 | `ADR-0057` |
| 整合性予算 | 価値の矛盾検出 | `ADR-0078` |

### 5. 価値仮説と現在の証拠状態

価値の実在は、証拠階層を付けて記録する。階層は T1（実在の第三者の実資料）、T2（Maintainer自身の、SUI自身を題材にしない実務利用）、T3（生成AIが演じる参加者）。T1 は必須ではない（外部協力者の確保を完了条件にしない）。T3 のみに基づく判定は `provisional` と書く。SUI自身を題材にした内部dogfoodは、いずれの階層にも数えない。

| 仮説 | 内容 | 現在の証拠 |
|---|---|---|
| H1 | 一次利用仕事と切替理由が、実在の仕事に対応する | 未検証（T1/T2/T3 いずれも未実施。内部dogfoodの示唆のみ） |
| H2 | 人間が残した根拠・異論・保留・関係をAI支援の途中でも落とさない（意味の保全） | 実装済み（LLM入力IR、`ADR-0069`）。`check-narrative` のscale方式が未決（入力約14万token、無料枠モデルでの参考値） |
| H3 | 初回の10分で、近さと保留を自分で判断する体験が得られる | 初回サンプルとgetting startedの題材を同期済み。説明確認は未実施 |

公開文書で価値の実証を主張するときは階層を明記する。T3 のみを根拠に「第三者が確認した」と書かない。

### 6. 機能・設計判断の優先順位判定

新しい機能案や構造改善は、一次価値への寄与を次の3つに分けて評価し、直接性と代替経路の有無で優先度を決める。

1. **意味の保全**: 根拠・異論・保留・関係を落とさない。中核価値に直結する。
2. **運搬の便利さ**: 外部AIとのやり取りなどを短くする。手動の代替があれば後回しにする。
3. **構造の整頓**: 内部の共通化や整理。通常経路が動いている限り急がない。

### 7. ADRへの反映規則

- 新規ADRは冒頭に **「価値への寄与」** を1〜3行で書く。対象は価値ループ（V0〜V4）、価値原則（P-xx）、不変条件（CVI-x）、または「安全 / 保守 / 運用のみ（価値への寄与なし）」のいずれか。
- 「価値への寄与なし」のADRは、一次価値を損なわないことだけを確認して起票する。優先度は §6 の3分類で判定する。
- 不変条件（CVI）を緩める提案は、本ADR・`ADR-0041` を更新するADRでのみ行える。
- 価値の定義（§1〜§3）を変える場合は、本ADRを改訂し、変更理由とどの証拠階層に基づくかを書く。
- ADRテンプレートを上記に合わせて更新する。三要素整合表・測定器整合欄は必須としない。

### 8. 運用系ADRの整理

次のADRは、現在の体制（1人＋生成AI）では運用上の力を持たないため `Superseded` とする（本文は履歴として残す）。

- フェーズ計画・バックログ: `ADR-0002`〜`ADR-0007`、`ADR-0012`
- 文書運用ゲート: `ADR-0022`〜`ADR-0025`
- 多エージェント運用・ブランチ統治: `ADR-0034`、`ADR-0045`
- 設計方法論と自律性レベル: `ADR-0047`、`ADR-0067`、`ADR-0075`

`ADR-0039`（個人OSS・プレリリースのガバナンス）は有効のまま、本ADRの §5 に沿って証拠階層を使う。`ADR-0037` の二軸スコアカードは、統治軸（CVI の非後退）だけを維持し、集計・Go/No-Go の運用は行わない。

## Consequences

- 価値の現在地と一次利用仕事を、`ROADMAP.md` と本ADRで読める。
- 新規ADRが価値へどう寄与するか、または寄与しないかが明示される。
- 価値の実在（H1）が未検証であることが、記録として残る。強い主張を避ける根拠になる。
