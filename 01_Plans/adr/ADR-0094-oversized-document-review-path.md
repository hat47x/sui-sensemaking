# ADR-0094: 送信上限を超えた文書を、根拠と異論を失わずに確認する導線

- Status: Proposed
- Date: 2026-10-09
- Deciders: Maintainer
- Scope: `03_Implement/backend/` の check-narrative 経路（LLM入力の上限と、`provider_request_too_large`）、`03_Implement/frontend/` の上限超過時の表示、`02_Architecture/llm_provider_spec.md`

## 価値への寄与

V2「構造化」とV3「レビュー」に寄与し、H2（人間が残した根拠・異論・保留・関係を、AI支援の途中でも落とさない）を守る。正本は `ADR-0089`。上限を超えた文書を、利用者が理由を知らないまま諦めたり、一部だけを黙って確認したりすると、根拠への戻り道と異論の記録が失われる。

## Context

- 上限超過は、2026-10-09 に `provider_request_too_large`（HTTP 413）として、送信前に拒否するようにした（#3203）。画面には「範囲を分けて、もう一度確認してください」と出るが、範囲を分ける操作はまだ無い。
- 上限は `MAX_LLM_PROVIDER_REQUEST_BYTES`（1 MiB、エンベロープ全体）。これはアプリ側の上限で、プロバイダの文脈長とは別の値である。DeepSeek の文脈長（約104万トークン）に対して、1 MiB の方が先に効く場合がある。
- check-narrative は全カードと全島を1回のプロンプトに入れる（意味の保全）。本文を生のUnicodeで書いた後の境界は、日本語本文で約2,300カード（合成文書、#3200 の計測）。実在の文書では未計測。
- 比較した選択肢:
  - **A. 拒否して理由を示すだけ（現状）。** 誤解は解消されたが、利用者は次の手を持たない。
  - **B. 島単位に分けて確認する。** 島の内側のカードは一緒に送る。島をまたぐ関係（`Edge`、所属、読み順の前後）は、分けた片側だけに残すと、確認結果が「関係が無い」と誤読される。分割した各部に、他部への参照（ID）と「この部分では確認していない関係」を明示する必要がある。
  - **C. 読み順の窓で分ける。** 実装は単純だが、読み順が文書の意味を表さない場合に、文脈が切れる。
  - **D. 上限を上げる。** 送信量と外部費用が増える。プロバイダごとに判断が必要で、SafeMode・送信境界の判断にかかわる。

## Decision

- 当面は **A** を維持し、**B** を次の候補として検討する。C は、利用者が島単位で分けられない場合の補助にとどめる。D は、この ADR では採らない。
- B を採る場合の最低条件:
  1. 分割した各確認結果に、「この部分で確認できなかった関係」を、ID で列挙して表示する。
  2. 分割前後で、カードと島の集合が一致することを検査できる（欠落が静かに起きない）。
  3. 分割は利用者が選ぶ。自動で分けて、結果を一つに統合しない（統合すると、部分の異論が平均化される）。
  4. SafeMode・未レビュー検査は、分割の各部に同じ規則で適用する。
- 非目標: 上限の値そのものの変更、プロバイダの選択、結果の自動統合。

## Consequences

- 期待される効果: 上限超過の理由が、利用者に伝わる。B を採れば、大きな文書でも根拠と関係の確認を続けられる。
- 想定される制約: B の実装には、分割の境界（島の選び方）と、関係の参照表示の設計が要る。ADR-0069（意味保全IR）との整合を確認する必要がある。
- 移行: B は UI と API の両方に影響する。API は `02_Architecture/api.md` を、同じ PR で更新する。

## Traceability
