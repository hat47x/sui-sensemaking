# ADR-0096: 読み取りAPIのSafeMode投影（ゲストと通常利用者）

- Status: Proposed
- Date: 2026-10-09
- Deciders: Maintainer
- Scope: `03_Implement/backend/src/sui_sensemaking_api/routes/docs.py`（`get_document`、ゲストと agent の分岐）、`03_Implement/frontend/src/domain/inquiry_bundle_safe_mode.ts`、`03_Implement/frontend/src/domain/policy/safe_mode.ts`、`02_Architecture/api.md`（`GET /docs/{doc_id}`）

本ADRは採否が未決の提案であり、コードは変更しない。行番号は `origin/main` の `cdd6bea`（2026-10-09 時点）で確認した。以後の変更で、行番号はずれうる。

## 価値への寄与

分類は「安全」である。価値ループ（V0〜V4）を直接進める機能ではない。非後退不変条件（CVI）の「SafeMode既定ON」と「人手レビュー昇格のみ」を、ゲストと通常利用者の読み取り経路でも守れるかを決める。一次利用仕事（ADR-0089 §1）への直接の寄与はない。

## Context

### 背景（なぜ今必要か）

SafeMode は、既定で ON の保護モードである（CVI、ADR-0089 §4）。その要点は、未レビュー本文を、共有・書き出しと AI への入力に出さないことである（`AGENTS.md` の安全不変条件）。他の利用者による読み取りを、この保護の範囲に含めるかどうかは、後の「未解決」3 で扱う。

2026-10-09 時点の main では、この保護がサーバの経路ごとに別々の形で入っている。共有と書き出しは、サーバが `export` と `share` を拒否し（`access_control.py:432-433`）、フロントが投影する（`inquiry_bundle_safe_mode.ts:1042`）。AI への入力は、サーバが未レビュー本文を拒否する（`llm_input_ir.py:673`）。agent の読み取りは、サーバが投影する（`docs.py:644`）。一方、ゲストと通常利用者の読み取りは、A1 契約の検証を通した保存本文をそのまま返しており、投影はない（`docs.py:839-897`）。

今この判断が必要になった理由は二つある。第一に、ADR-0080（2026-08-26 Accepted）でゲストの読み取りが入り、その CHK-X1 と CHK-D4 は、ゲストも通常利用者と同じ SafeMode 制約を受けると定めた。第二に、ADR-0093 の agent 向け投影が main に入り、サーバが読み取りを投影できることが、同じ場所で確認できるようになった。投影の規則はフロントの TypeScript にだけあり、サーバには同じ規則がない。

防ぎたい失敗は三つある。

1. ゲストや API を直接呼ぶ利用者が、未レビュー本文を、フロントの表示規則を経由せずに受け取る。
2. 投影の規則が TypeScript（共有・書き出し）と Python（読み取り）に二重化され、片方だけが更新される。
3. 読み取りに投影を入れた結果、人のレビュー作業が止まる。または、空にされた本文が保存される（推測。後述）。

### 現状（コードで確認した事実）

| 経路 | 現状 | 根拠 |
|---|---|---|
| 通常利用者の `GET /docs/{doc_id}` | A1 契約の検証（`docs.py:120-209`）を通した保存本文を返す。SafeMode の投影はない。`safe_mode=True` は認可の入力として固定される | `docs.py:839-897`、`docs.py:851` |
| ゲストの読み取り | 付与された `doc_id` だけを、読み取り専用で認める。違いは認可の分岐だけで、本文は通常利用者と同じ関数が返す | `docs.py:232-296`（付与の確認は245行目、許可の判定の理由は294行目） |
| agent の読み取り | 許可リストによる投影。`textReviewed` が `true` でないカードの本文を空にする | `docs.py:213-219`、`docs.py:644-714`、`docs.py:862-864` |
| 共有・書き出し | サーバは `export` と `share` を SafeMode で拒否する。フロントは `deriveDocumentSafeModeProjection` で投影する | `access_control.py:432-433`、`inquiry_bundle_safe_mode.ts:1042-1087`（呼び出し: `export/canvas_svg.ts:98`、`export/bundle_export.ts:220`） |
| AI への入力 | サーバが未レビュー本文を拒否する（ADR-0069 の IR 層で、防御の第二層として働く） | `llm_input_ir.py:673`（`_enforce_safe_mode`） |
| アプリ内表示 | `SafeModePolicy.canExposeText` は、`ui` 文脈では SafeMode が ON でも `true` を返す | `03_Implement/frontend/src/domain/policy/safe_mode.ts:15-28` |

読み取り応答には、投影とは別に、契約の検証の副作用がある。`DocumentV1` には `model_config` の指定がない（`models.py:1635-1729`）。そのため、Pydantic の既定値 `extra="ignore"` に従い、`DocumentV1` にない上位の項目は応答から落ちる。これは SafeMode の投影ではなく、検証の結果である。

注意すべき点が二つある。

第一に、現行の `SafeModePolicy` では、アプリ内表示の本文は SafeMode で制限されていない。このため、ADR-0080 の CHK-D4 にある「カードSafeMode制約を通常利用者と同様に適用する」の「制約」が、共有・書き出しだけを指すのか、アプリ内表示を含むのかは、コードからは決まらない。さらに、ゲストがアプリ内で本文を読むことを、`SafeModePolicy` の `share` 文脈に当たるとみなすかどうかも決まらない。ADR-0080 は、招待を「特定の個人」宛の意図として定義している（同ADRの表、データ設計の業務欄、119行目）。そのため、ゲストへの提供を共有に近いものとして読む余地はある（推測）。

第二に、`api.md:72` は、本文の取得を「`GET /docs/{doc_id}` のSafeMode経路」と書いている。しかし、`GET /docs/{doc_id}` で投影されるのは agent 向けだけである。この文言が、投影を前提にしたものか、単に本文を取得する経路を指すのかは、文書からは確認できない（推測）。

### 関連する前例と用語

- ADR-0068 は、AI 入力の SafeMode 保護がフロントだけで強制されている問題を指摘した（同ADRの「帰結」、50行目）。その後、ADR-0069 の IR 層でサーバ側の強制（`_enforce_safe_mode`）が入った。本ADRの問題は、フロントだけが守る経路が残るという同じ構造を、読み取りに当てはめたものである。
- ADR-0071 の「読み取り用の投影」は、DB から作る読み取りモデル（read model）の意味で使われている。本ADRの「SafeMode投影」とは別の概念である。混同を避けるため、本ADRでは「SafeMode投影」と書く。ここでいう投影とは、保存された本文から、規則に従って一部を隠す、または空にした形を作ることを指す。
- 「未レビュー本文」は、`textReviewed` が `true` でないカードの本文を指す。`docs.py` の agent 向け投影と同じ判定である。
- `test_ts_python_contract_drift.py` は、TypeScript と Python の型のフィールド集合の差を検出する（冒頭の説明）。その説明では、比較の対象はフィールド集合であり、方針表の値は挙がっていない。

### 比較した選択肢

- **A**: 全員の読み取り（ゲストと通常利用者を含む、アプリ内読み取り）に、サーバ側で SafeMode 投影を入れる。
- **B**: ゲストの読み取りだけに、サーバ側で投影を入れる。通常利用者の読み取りは現状のままにする。
- **C**: 現状を維持する。投影は、フロントの共有・書き出しと、agent 向けのサーバ投影だけに残す。

## Decision

### 推奨（未採用）

保守者の判断を拘束しない推奨として、A の方向を提案する。本ADRは Proposed であり、採否は未決である。A を採るには、「未解決」の 1 から 4 を先に決める必要がある。特に、アプリ内表示の扱い（1）、レビュー者の扱い（2）、SafeMode の状態の伝え方（4）が決まらなければ、A は実装へ進めない。

A を推奨する理由は次のとおりである。CHK-X1 は、ゲストも「通常利用者と同じSafeMode制約を受ける」と定めている。A は、経路（ゲストか通常利用者か）による例外を置かずに、同じ規則を読み取り全体へ当てられる。

B は、ゲストだけ制約を強めるため、「同じ」を満たさない。さらに、通常利用者の読み取りには、同じ空白が残る。

C は、CHK-X1 と CHK-D4 を満たすかどうかを、「制約」の定義の問題として先送りする。この定義はまだ決まっていない。そのため、C の下では、要件を満たしたとも満たしていないとも書けない。

A の代償も明記する。A は、現行の `SafeModePolicy`（`ui` 文脈は制限されない）からの変更を含む。さらに、人が未レビュー本文を読んで確認する作業と両立させる設計が必要になる。この両立が決まらないまま投影を入れると、レビューの動線が止まる。

### 投影の移植方法（選択肢。未決）

TypeScript のフィールド方針表（`inquiry_bundle_safe_mode.ts:172-196` の `DOCUMENT_FIELDS`。`satisfies Record<keyof DocumentV1, FieldPolicy>` により、全フィールドの方針を型で網羅させている）を、Python にどう移すかを、次の三つの選択肢として挙げる。

- **P1: フィールド方針表を単一の正本にし、TypeScript と Python の両方で検査する。** 表を共有のデータとして置き、両言語で、フィールドの網羅と方針の値を検査する。表の変更は両側の検査に現れる。ただし、`rebuild`（本文を作り直す処理）の実装は両言語に残る。また、`test_ts_python_contract_drift.py` の仕組みを、方針値の比較へ広げる必要がある。
- **P2: 読み取り API が、投影済みの応答だけを返す。** 規則の実装を Python の一か所にまとめ、フロントは投影を再計算しない。ただし、アプリ内表示の仕様（未解決 1 と 2）が先に必要になる。また、共有・書き出しの TypeScript 投影は残るため、規則は二か所に残る。
- **P3: 入力と期待出力の fixture を両言語で共有する。** 同じ期待値を、TypeScript と Python の両方のテストで読む。言語が変わっても同じ期待値で検査できる。ただし、fixture を更新するときは、両側の確認が要る。

比較の観点は、規則の正本が一つか、表の変更で検査が失敗するか、フロントの再計算が残るか、の三つである。本ADRは、いずれも選ばない。

### 非目標

- 投影規則そのもの（`DOCUMENT_FIELDS` の `preserve` / `redact` / `omit` / `rebuild` の値、`_agent_document_view` の除外項目）は変更しない。
- agent の読み取りの投影（ADR-0093）は変更しない。
- 書き込み、export、share の拒否（`access_control.py:432-433`）と、AI 入力の拒否（`llm_input_ir.py`）は変更しない。
- SafeMode の既定値（ON）は変更しない。
- ゲストに本文を見せるかどうかの業務判断は、本ADRでは決めない。その判断は、ADR-0080 の招待の要件に依存する。
- 本ADRはコードを変更しない。

## Consequences

### 各案の影響

| 観点 | A（全員） | B（ゲストのみ） | C（現状維持） |
|---|---|---|---|
| 読み取り API の契約（`GET /docs/{doc_id}`） | 未レビュー本文が空になる、または印になる。応答の形は変えられる（agent 向けと同じく、id と構造は残せる）。`api.md:65-68` の更新が要る | ゲストの応答だけが変わる。通常利用者の応答は変わらない。ゲストだけ異なる契約を `api.md` に書く必要がある | 変更なし |
| フロントの表示（`App.tsx:2408` の読み込み） | 未レビュー本文が画面に出ず、人が確認できなくなる（推測。`App.tsx:5987` の `handleCardTextReviewedChange` と `App.tsx:12265` の文字編集は、本文を読んだうえでの人の操作を前提にしている） | ゲストの画面で、未レビュー本文の代わりに、未レビューであることを示す表示が必要になる | 変更なし |
| 既存テスト | `test_docs_roundtrip.py:1063-1067` は、`textReviewed` を持たないカード（`_sample_payload`、79-98行目）の本文を、GET の応答と完全一致で比べる。投影を入れると、この期待値の変更が要る。`/docs/` を読む backend テストは、grep で約27ファイルある（本文を検査するものは一部） | `test_guest_docs_http_authorization.py` は `cards: []`（36行目）のため、本文を検査していない。ゲストの本文の投影を検査する新しいテストが必要になる | 変更なし |
| SafeMode の状態と後方互換 | `get_document` は `safe_mode=True` を固定する（`docs.py:851`）。フロントは GET に SafeMode の状態を送らない（`client.ts:396-403`）。SafeMode を OFF にした利用者に何を返すかが決まっていない。投影を入れた場合、配布済みのフロントは空になった本文を受け取る | 同じ問題が、ゲストの経路に残る | 変更なし |

A には、本文の保存に関する影響もある。`PUT /docs/{doc_id}` は文書全体を置き換える（`api.md:28`）。ETag は保存本文から計算され（`docs.py:860`）、PUT は、その値が現行の保存本文の ETag と一致すれば受け付ける（`docs.py:1024-1026`）。投影済みの応答から得た ETag も、保存本文と同じ値になる。そのため、投影済みの本文を基にした保存は、ETag の検査を通ってしまう。空にされた本文が保存されるおそれは、この組み合わせから生じる（推測。フロントが投影済みの本文を PUT に使うかどうかは、確認していない）。

### 未解決

1. **投影の対象の範囲。** アプリ内表示（`ui` 文脈）に SafeMode を及ぼすかどうか。現行の `SafeModePolicy` は及ぼしていない（`policy/safe_mode.ts:15-28`）。
2. **レビュー者の扱い。** 未レビュー本文を、確認の作業をする利用者に見せるかどうか。見せないなら、どこで確認するのか。
3. **CHK-D4 の「制約」の意味。** 共有・書き出しの制約だけを指すのか、アプリ内表示を含むのか。ゲストの閲覧を、`SafeModePolicy` の `share` 文脈に当たるとみなすのか。
4. **SafeMode の状態の伝え方。** `get_document` の `safe_mode=True` の固定（`docs.py:851`）を、どう変えるか。クエリやヘッダを足すのは、契約の変更になる。これは ADR-0068 の D1（SafeMode の状態を誰が宣言し、サーバがどう知るか）と同じ論点である。
5. **投影の方式。** agent と同じ許可リストの方式（`docs.py:644-714`）にするか、TypeScript のフィールド方針表のような網羅型（新しいフィールドは、方針の指定がないとコンパイルが通らない）にするか。新しいフィールドが増えたときに、既定で出る側と出ない側が逆になる。
6. **後方互換。** 配布済みのフロントが空の本文を受け取ったときの表示、PUT の全体置換との組み合わせ（上記の推測）、投影後の応答に保存本文の ETag を返してよいかどうか。
7. **`api.md:72` の文言。** 「`GET /docs/{doc_id}` のSafeMode経路」が何を指すかを確認し、実装と文書のずれを解消する。
8. **既存の露出。** 投影を入れても、過去に読まれた本文の露出は取り消せない。本ADRは、この点を主張しない。

### 非主張範囲

- 本ADRは、読み取りに投影が必要だと確定させるものではない。
- 現状で、ゲストが保存本文を読めることが SafeMode の違反かどうかは判定しない。判定には、未解決 3 の定義が要る。
- 投影の規則（どのフィールドを空にするか）の妥当性は判断しない。その判断は、規則そのものを変える別の決定で扱う。
