# ADR-0097: AIタスクごとのLLM設定を、権限をもつ管理者が実行時に設定できるようにする

- Status: Proposed
- Date: 2026-10-12
- Deciders: Maintainer
- Scope: `03_Implement/backend/src/sui_sensemaking_api/`（`llm/provider.py`、`settings.py`、`routes/ai.py`、`routes/ai_relations.py`、`routes/model_registry.py`、管理面の新しい経路）、`03_Implement/backend/scripts/evaluate_check_narrative_omission.py`、`02_Architecture/api.md`、`02_Architecture/runtime_parameter_registry.md`

本ADRは採否が未決の提案であり、コードは変更しない。行番号は `origin/main` の `4bd493f9`（2026-10-12 時点）で確認した。以後の変更で、行番号はずれうる。

## 価値への寄与

分類は「運用」であり、意味の保全に当たらない。ADR-0089 §6 の3分類では便利さに近く、手動の代替（環境変数の変更と再起動）があるため、後回しにできる。§7 の区分では「運用のみ（価値への寄与なし）」に当たる。出典・異論・保留・人間の判断権を、新しく残せるようにする変更ではない。

むしろ、設定を誤ると意味の保全を損なう。`check-narrative` は、島を1つだけ物語から欠いた300カードの入力で、思考モード `enabled` なら20回中20回検出した。`disabled` の小標本では6回中3回だった（根拠は Context）。管理者が測定も記録もなくこの差を越えられるようになれば、島の欠落の見逃しが、気づかれないまま増えうる。そこで本ADRは、設定の自由度を足すより先に、意味の保全を損なう値を受け付けない制約（許可リスト、測定ゲート、変更の記録）を固定する。起票は、一次価値を損なわないことの確認だけで足りる（ADR-0089 §7）。

実装へ昇格させる根拠は、ROADMAP の原則（同じ摩擦が実際の利用で再現したものから実装へ昇格させる）に従い、次のいずれかの記録とする。現時点で、再現した摩擦の記録はない。あるのは Maintainer の要望と、評価のために環境変数を切り替えた経験だけである。

1. T2（Maintainer 自身の、SUI 以外の実務）で、AIタスクの設定を変える必要が複数回起き、その都度の再起動または再デプロイが作業の妨げになった。
2. `saas-multitenant` で複数のテナントが実際に稼働し、テナントごとに設定を変えたいという具体的な要請があった。
3. 設定の変更でAIの出力が変わった事例があり、誰がいつ何を変えたかを後から確認できず、判断に困った。

いずれも起票時点では未発生である。本ADRは設計の先行固定であり、実装の着手を決めない（「着手の条件」を参照）。

## Context

### 背景

最終判断のタスク（`check_narrative`、`detect_contradiction`）は、2026-10-09 の測定を受けて、DeepSeek の思考モードの既定を `enabled` にした（`llm/provider.py:165-179`）。タスクごとの上書きは、環境変数 `SUI_DEEPSEEK_THINKING_TASK_MAP` でできる。管理者がタスクの種類ごとに実行時に設定できる形は、ROADMAP と `runtime_parameter_registry.md`（121行目）で今後の課題とされている。Maintainer の要件は、最終的に、タスクの種類ごとに、適切な権限をもつ管理者が個別に設定できることである。

この仕組みを先に実装すると、管理者が最終判断の既定を、測定なしに弱められる経路ができる。誰が、どの範囲で、どの値まで変えられるかを、実装の前に決めておく必要がある。

### 測定による動機

`03_Implement/backend/scripts/evaluate_check_narrative_omission.py` で、300カード・30島の合成データから島を1つ欠かした入力を測った。値は、ROADMAP の「未完の作業」1 と `runtime_parameter_registry.md`（121行目）にある。

| 条件 | 欠落の検出 | 対照の誤検出 | 備考 |
|---|---|---|---|
| DeepSeek（`deepseek-flash`）、`enabled`、20回 | 20/20（Wilson下限0.84） | 2/20 | 基準（下限0.8）を満たす |
| 同、`enabled`、6回（2026-10-09の小標本） | 6/6 | 記録なし | 既定を `enabled` にした根拠 |
| 同、`disabled`、6回（同上） | 3/6 | 記録なし | Wilson 95%区間は約0.19から0.81 |
| `nvidia/nemotron-3-super-120b-a12b:free`（OpenRouter）、`enabled`、20回 | 11/20（下限0.34） | 0/20 | 基準未達 |
| 同、`disabled`、20回 | 0/20 | 記録なし | 基準未達 |

DeepSeek の `disabled` を20回で測った値は、リポジトリで確認できなかった。6回中3回では、約半分とは言えても精度は低い。同じ `enabled` でも、モデルによって結果が大きく違う。このため、設定の許否は、モデルと思考モードの組ごとの測定で決める。

### 防ぎたい失敗

1. 管理者、または侵害された管理者の資格情報が、測定なしに最終判断の思考を止める。島の欠落が見逃され、しかも後から確かめられない。
2. 共有SaaSで、あるテナントの設定が、ほかのテナントの最終判断の既定や、共有の外部予算に影響する。
3. 設定の入口が増えた結果、registry と許可リストが定める宛先の境界を、設定が迂回する。
4. 環境変数と実行時の設定が二重になり、どちらが効いているか分からなくなる。
5. 設定の保存先が壊れたとき、黙って別の設定で動く。

## Decision

### 比較した選択肢

| 案 | 内容 | 利点 | 欠点 | 判断 |
|---|---|---|---|---|
| A | 環境変数だけを使う（現状維持）。D8 の前提整備だけを行う | 書き込み面が増えない。設定がデプロイの管理下にあり、再現しやすい。単一テナントの自己ホストには足りる | 変更に再起動が要る。テナントの管理者は何も設定できない。製品内に変更の履歴が残らない。SaaSで「テナント別」を表せない | 当面の既定。D8 は A の範囲で先に行える |
| B | モデル registry の行に列を足す（例 `thinking_mode`、`task_defaults`） | 既存の管理経路、認可、`expectedRevision` を再利用できる。差分が小さい | 軸が合わない。方針の単位はタスクだが、registry の行はモデルであり、「タスクとモデルの組」を1列で表せない。registry はテナントを持たないため、テナント範囲を置けない。モデルの行を変えると、そのモデルを使う全タスク・全テナントへ影響する。`capabilities` は256文字の自由な文字列で、型の検査がない。履歴は `updated_at` だけになる | 採らない。registry は「何が呼べるか」の正本として残し、方針表から参照する |

### 提案する決定

**C を採る。タスク別の方針表を別に持ち、範囲を、プラットフォーム（C1）とテナント（C2）の2つにする。まず C1 を入れ、C2 は需要の証拠が出てから足す。環境変数は、起動時の既定と、方針表に行がないときの代替として残す。**

理由は4つある。方針の単位がタスクであり、C だけが軸を合わせられる。既存の2つの管理面（コントロールプレーンと Tenant Admin、ADR-0059 D9）に、範囲がそのまま対応する。最終判断を弱める経路を、測定ゲートと変更の記録で閉じられる。環境変数を残すので、`SUI_LLM_PROVIDER=none` を含む現行の動作を変えない。

### D1. 設定できる項目と、タスクの一覧

- 項目は2つに限る。`thinkingMode`（`disabled` か `enabled`）と、`modelId`（registry に登録された active なモデルのID）である。値は型付きで、自由な文字列を受け付けない。
- タスクの一覧は、コードが持つ閉じた集合とする。各タスクに段階（`intermediate` か `final_judgement`）を持たせる。管理者は、タスクを追加できず、段階も変えられない。段階が `unknown` のタスクは、分類されるまで設定を受け付けない。
- 最終判断のタスクで実行時に変えられるのは、`thinkingMode` だけである。変更には D4 のゲートを通す。`modelId` は、第1段階では環境変数と registry のままにする。モデルを替えると評価をやり直す必要があり、その結果を載せる場所が、registry の `capabilities`（自由な文字列）にないためである。
- 次は設定の対象にしない。`max_tokens`、`temperature`、プロンプト、SafeMode、IR（LLM入力の中間表現、ADR-0069）の投影、プロバイダの宛先と資格情報、タスクの段階の所属。いずれも、何を外へ送るか、または何を守るかを決めるものである。本ADRが変えるのは、同じ入力を、どのモデルで、思考ありかなしで処理するかだけである。

### D2. 解決順序

項目（`thinkingMode`、`modelId`）ごとに、次の順で、最初に値がある層を採る。

| 順 | 層 | 備考 |
|---|---|---|
| 0 | `SUI_LLM_PROVIDER=none` | 方針に関わらずLLM呼び出しを止める（`provider.py:1118`）。方針はAIを有効にしない |
| 1 | リクエストの `model` | 中間タスクの `modelId` だけ。従来どおり。思考モードには、リクエスト単位の指定を作らない |
| 2 | テナントの方針（C2） | 中間タスクだけ。プラットフォームの方針が `tenantOverride=allowed` のタスクに限る |
| 3 | プラットフォームの方針（C1） | |
| 4 | 環境変数 | `SUI_DEEPSEEK_THINKING_TASK_MAP`、`SUI_LLM_TASK_MODEL_MAP`、`SUI_LLM_HIGH_REASONING_MODEL`、`SUI_DEEPSEEK_THINKING_MODE`。順序は現行のまま |
| 5 | コードの既定 | 最終判断の `thinkingMode` は `enabled`。モデルはプロバイダ既定 |

解決の後に、次の関門を、方針があっても外さない。`_assert_model_allowed`（テナントの許可リスト、registry の active、プロバイダの利用可否）、SafeModeと未レビュー本文の拒否、IRの投影、`max_tokens`、外部送信の許可（`SUI_LLM_ESCALATION_ENABLED` など）である。

### D3. 誰が何を変えられるか

| 実行形態 | 主体 | 変えられるもの | 認可 |
|---|---|---|---|
| 単一テナント（`local-dev`、`evaluation`、`enterprise-production`） | デプロイ管理者 | その配備全体の方針。最終判断の `thinkingMode` を `disabled` にする変更は、測定ゲートを通す | コントロールプレーンの段階A（`SUI_ADMIN_API_KEY`）。`local-dev` と `evaluation` で鍵が未設定なら、コントロールプレーンが開く既存の挙動に従う（ADR-0072） |
| `saas-multitenant` | プラットフォーム運用者 | 全テナントの既定、`tenantOverride` の許可、最終判断の `thinkingMode`（測定ゲート付き） | コントロールプレーンの段階B（識別できる主体）。認可は、既存の registry の管理経路と同じ `require_control_plane_authorization` を使う。専用の capability を足すかは、未解決 6 とする。段階Aは、中間タスクの変更と、最終判断を強める変更に限る。段階Aは主体を識別できず、ブートストラップ専用だからである（ADR-0072 D1） |
| `saas-multitenant`（第2段階） | Tenant Admin（テナント管理者） | 自テナントの、中間タスクの上書き。`tenantOverride=allowed` のタスクだけ | `llm.policy.manage`（Tenant Admin に足す新しい capability）。テナントは、サーバーが解決したアクティブなテナントとする（ADR-0063 D8）。テナント単位のAPIとして、ADR-0061 D2 の `tenantSessionVersion` の前提条件を要求する |
| 共通 | 一般の利用者、ゲスト、agent | 変更できない。中間タスクのリクエスト単位の `model` 選択は、従来どおり許可リストの内側で行う | 変更なし |

テナントがほかのテナントの最終判断の既定を弱められないように、次の構造にする。

- テナントの行は、キー `(tenantId, task)` で保存し、サーバーが解決したアクティブなテナントのリクエストにだけ効く。テナントIDを、ヘッダーや本文から受け取らない。
- Tenant Admin が書けるのは、中間タスクの行だけである。最終判断の行、プラットフォームの行、`tenantOverride` は書けない。
- 最終判断の既定を弱める変更は、プラットフォームの行にしか存在しない。D4 のゲートを通す必要があり、`saas-multitenant` では識別できる主体も要する。
- 方針は、宛先を増やさず、`max_tokens` を変えない。共有の外部予算（ADR-0082、Proposed）を、テナントの設定が消費しうる点は、未解決に残す。

### D4. 変更時の検査（保存の前）

1. 形。未知のタスク、未知の項目、列挙外の値、余分なフィールドは、422で拒否する。
2. 値。`modelId` は registry の active なモデルであり、テナントの行では、そのテナントの許可リストに含まれること。
3. 向き。変更を3つに分類する。`strengthen` は、最終判断の `thinkingMode` を `enabled` にする、行を消す、`tenantOverride` を `forbidden` に戻す変更である。`weaken` は、最終判断の `thinkingMode` を `disabled` にする変更である。`neutral` は、中間タスクの変更である。強める変更は、証拠なしで常に受け付ける。弱める変更は証拠を要し、`saas-multitenant` では識別できる主体も要する。
4. 証拠。弱める変更には、測定ゲート（後述）のレポートの要約を添える。サーバーは、許可リストのキーと、値の基準だけを検査する。証拠は、（タスク、プロバイダ種別、実効のモデルID、思考モード）の組に結びつける。
5. 排他。`expectedRevision` を必須とする。欠落は428、不一致は409とし、許可リストの更新と同じ契約にする。
6. 原子性。方針の変更と、その変更イベント（D6）を、同じトランザクションで書く。イベントを書けなければ、変更を適用しない（fail-closed）。
7. 秘密。入力に、資格情報を受け取るフィールドを設けない。変更の理由は、閉じた集合の `reasonCode` だけにする。

### D5. 実行時の扱い（呼び出しの前）

1. 解決はルート層で、リクエストごとに1回行う。実効の `thinkingMode`、由来の層、方針の版（revision）を `LLMRequest` に載せ、プロバイダへ渡す。プロバイダ層は、DBを読まない。既存の `resolve_thinking_mode_for_task` は、解決済みの値を持たない呼び出し（評価スクリプト、テスト）の代替として残す。
2. キャッシュは、第1段階では持たない。変更は、次のリクエストから効く。持つ場合は、`deployment + tenantId + task + policyRevision` をキーにし、失効できる設計にする。ADR-0059 D9 の権限キャッシュと同じ考え方である。
3. 行がなければ、次の層へ進む。行があっても、読めない、版が未知、値が許可の外、証拠が今の実効モデルと一致しない、のいずれかなら、呼び出しを拒否し、安定したエラーコード（例 `llm_task_policy_invalid`）を返す。最終判断では、既存の保留（hold）経路に入る。別の層へ黙って落とさない。
4. プラットフォームが `tenantOverride` を撤回したとき、既存のテナントの行は適用しない。実効値の読み取りには `suppressed` と表示する。
5. 実効の `thinkingMode`、由来の層、方針の版を、LLM呼び出しの監査へ入れる。

### D6. 変更の記録

方針の変更は、新しい追記専用のイベント表に、変更ごとに1行を残す。既存の `admin_audit_events` に値を足さない。あの表は本体を保存しない契約（ADR-0035）で、記録の失敗を許す（fail-open）ためである。

- 残すもの。`eventId`、`occurredAt`（UTC）、`scope`（`platform` か `tenant`）、`tenantId`（テナント範囲だけ。サーバーが解決した値）、`task`、`field`、`before`、`after`（許可リストの列挙値と registry のIDだけ）、`direction`、`actorRefHash`（識別できる主体、または段階Aの資格情報のフィンガープリント）、`authStage`（`A`、`B`、`tenant-admin`）、`revisionBefore`、`revisionAfter`、`requestId`。
- 弱める変更では、証拠の要約（許可リストのキーだけ）と、その正規化したJSONのSHA-256を足す。
- 入れないもの。トークン、APIキー、`apiKeyRef` の値、プロンプト、カード本文、文書の題名、生のIdP識別子、自由記述。
- 見られる範囲。プラットフォームのイベントはコントロールプレーンだけ、テナントのイベントは、そのテナントの `audit.read` をもつ主体だけである。
- 監査ディスパッチャー（`SUI_AUDIT_TRANSPORT`）へも、同じ内容を送る。正本はDBの行とし、ディスパッチャーへの送信の失敗は、変更を止めない。

### D7. 環境変数の位置づけと、実効値の読み取り

- 環境変数は、起動時の既定と、方針表に行がないときの代替として残す。削除の予定はない。
- 環境変数の値を、方針表へ自動で写さない。写すと、環境変数を直した後も方針表の古い値が効き続け、二重管理が見えなくなるためである。registry の起動時シード（`model_registry_seed.py`）とは、この点で扱いを変える。
- 代わりに、タスクごとの実効値を読む経路を同時に用意する。実効の `thinkingMode` と `modelId`、由来の層、環境変数との食い違い、適用外（DeepSeek 系以外のトランスポートでは `thinkingMode` が送られない）、`suppressed` を返す。秘密は含めない。

### D8. 前提整備（方針表より前に、単独で行える）

| # | 内容 | 理由 |
|---|---|---|
| P1 | LLM呼び出しの監査に、実効の思考モードを含める | 今は、結果がどの思考モードで得られたかを確かめられない（現状の表） |
| P2 | タスクの一覧を、コード上の閉じた集合にし、`propose_opposing_viewpoint` に段階を与える | D1 の前提 |

| P4 | 11タスクすべてを、同じ解決と `_assert_model_allowed` に通す | 3タスクが、registry と許可リストの検査を通らない。方針だけが通っても、境界が揃わない |

### 非目標

- SafeModeの既定とAPI境界での強制（ADR-0068）、未レビュー本文の拒否、IRの投影（ADR-0069）を変えない。
- AI出力を提案のみとすること、`human_reviewed` を人間だけが設定することを変えない。
- 外部送信の許可（registry、許可リスト、`SUI_LLM_LARGE_SCALE_*`）と宛先を、方針から変えない。方針表は資格情報を持たない。
- 最終判断の `modelId` の実行時の変更と、テナント管理者による最終判断の変更は、本ADRでは決めない。
- 利用者単位、キャンバス単位の設定（ADR-0065 の Phase 3）、管理コンソールのUI（ADR-0079）は扱わない。CLIとAPIが先である。
- サーバーが評価を実行し、外部プロバイダへ送ることは行わない。

### 測定ゲート

最終判断のタスクで `thinkingMode` を `disabled` にする設定は、次をすべて満たすときだけ受け付ける。

1. そのタスクの評価が存在する。起票時点で `origin/main` にあるのは、`check_narrative` 用の `evaluate_check_narrative_omission.py` だけである。`detect_contradiction` には同等の評価がない。評価が整うまで、その `thinkingMode` は `enabled` に固定する。
2. 評価を、合成データだけで、候補の設定を適用した環境で実行する。バックエンドのルートで、`SUI_TOKEN_MEASUREMENT_OPT_IN=1 python scripts/evaluate_check_narrative_omission.py --provider <名前> --model <モデルID> --islands 30 --trials 20 --execute` を実行する。候補の設定（例 `SUI_DEEPSEEK_THINKING_TASK_MAP=check_narrative=disabled`）をこの環境に与え、レポートの `thinking_modes_seen` が `["disabled"]` になることを確かめる。
3. 基準は、レポートの `meets_minimum` が true であることとする。検出率の Wilson 下限が0.8以上で、`provider_errors` と `unreadable_responses` が0である。20回の試行では、20回中20回だけが通る。19回では下限が0.764になる。
4. `control_false_positives` と `max_input_tokens_reported` を、変更の記録に残し、人が確認する。誤検出の上限は未決である（`enabled` の実測は2/20）。
5. 結果は、（タスク、プロバイダ種別、実効のモデルID、思考モード）の組に結びつく。どれかが変われば証拠は無効になり、D5 の3により呼び出しが拒否される。
6. 費用は、40回（欠落20、対照20）で約1.2ドルの上限見積もりである（ROADMAP の1回約0.03ドルから計算した）。

このゲートの限界を、先に書いておく。

- 測るのは、30島・300カードの1点だけである。ほかの規模は測っていない。
- 欠落は「島1つ」の1種類で、カード1枚や関係、異論の欠落は測っていない。
- 20回は足切りの基準であり、保証ではない。プロバイダが同じモデルIDの中身を更新すれば、結果は古くなりうる。
- レポートは、管理者が自分の環境で実行して提出する自己申告である。サーバーは、真正性を検証できない。検査できるのは、許可リストのキーと値の基準だけである。
- 環境変数は、デプロイの管理権限をもつ人が、従来どおり直接書き換えられる。このゲートが検査するのは、製品の管理面から行う変更だけであり、環境変数の経路は検査しない。

## 移行と互換

1. 方針表が空なら、全タスクの実効値は現行と同じである。マイグレーションは空の表を作るだけで、データの移行はない。
2. 環境変数は今までどおり有効で、起動時の検証も変えない。P3 のタスク名の検証は、既存の誤記を拒否に変えうるため、まず警告にとどめる。
3. 環境変数が最終判断を、測定なしに `disabled` にしている構成は、第1段階では挙動を変えない。実効値の読み取りと、LLM呼び出しの監査（P1）に現れるだけにする。`saas-multitenant` で起動を拒否するかは、未解決とする。
4. P4 は挙動が変わる。既定モデルが registry で active でない構成や、空でないテナントの許可リストに既定モデルがない構成では、`re_layout`、`suggest_merges`、`summarize_island_relation` が、新しく403になる。配備前に、registry と許可リストの確認を運用手順へ入れる。
5. 戻し方は、方針の行を消す、または表を落とす（downgrade）ことである。環境変数とコードの既定へ戻る。これが成り立つように、環境変数を権威のある下位層として残す。
6. フロントエンドと `DocumentV1` は変えない。`/ai/provider-status` も変えない。契約は、実装と同時に、`api.md`、`runtime_parameter_registry.md`（121行目の「将来は〜」と優先順位）、`llm_provider_spec.md`（74行目）、ADR-0065（D2 のテナント層の実現方法）へ反映する。

## Consequences

- 期待される効果。再起動なしに設定を変えられる。誰がいつ何を変えたかを追える。測定ゲートを、製品の手順として持てる。テナント別の運用へ進めるようになる。
- 代償。書き込み面と表が増える（プラットフォームの方針、テナントの方針、変更イベント）。設定の所在が2つ（環境変数と方針表）になり、解決順序を理解する負担が増える。テナント別に挙動が違うため、支援では、実効値と由来の確認が必要になる。
- 意図した制約。監査の保存先が使えないときは、設定を変えられない。変更の可用性より、記録が残ることを優先する（fail-closed）。
- 範囲の外。変更後の継続的な品質監視は含まない。回帰は、評価スクリプトを再実行しないと見つからない。
- 残る危険。測定の記録は自己申告であり、管理者が偽ることを防げない。信頼の境界は、権限をもつ管理者にある。

## 未解決

1. 昇格の判定。「同じ摩擦が再現した」を、何件のどの記録で満たしたと見なすか。T2 の記録に何を残すか。
2. 評価レポートの出自。P5 で項目を足しても自己申告である点は変わらない。サーバーが、合成データだけを送って評価を実行する形を、将来採るか。
3. 証拠の失効条件。モデルの中身の更新、プロンプトの変更、規模の変化を、どう検知して失効させるか。
4. `detect_contradiction` の評価。何を「見逃し」と数えるか。`check_narrative` の島の欠落とは、定義が異なる。
5. 対照の誤検出の基準。`meets_minimum` に含まれていない。上限を置くか。
6. プラットフォームの権限。既存の registry の管理経路と同じコントロールプレーン認可（段階Bでは `tenant.provision`）を流用するか、専用の capability を足すか。`tenant.provision` はアクティブなテナントに束縛された権限であり（`api.md` の監査経路の記述）、全テナントに効く方針の変更を許す根拠として足りるかは、決まっていない（推測）。
7. 最終判断を、テナント管理者へ開く条件。テナント自身の実データでは測れない（実在の機微資料を外部へ送らない）。
8. 環境変数の測定なしの `disabled` を、`saas-multitenant` の起動拒否へ引き上げるか。
9. 許可の範囲を狭めたときの扱い（モデルの無効化、`tenantOverride` の撤回）。影響を受けるテナントを事前に一覧するか、猶予を置くか。
10. 共有の外部予算（ADR-0082）との関係。テナントの方針が `enabled` や高価なモデルを選ぶと、ほかのテナントの枠を使う。テナント別の上限が要るか。
11. 変更の通知と、変更より前に出た最終判断の結果の扱い。過去の結果の再評価は求めず、使われた設定を監査から辿れるだけでよいか。
12. 変更の理由。自由記述を許すと、秘密が貼られうる。`reasonCode` の閉じた集合だけにするか。
