# ADR-0108: 段階2の提案ingestは必要性が観測されるまで作らない

- Status: Accepted（2026-11-01）
- Date: 2026-11-01
- Deciders: Maintainer（Issue #3271 の自律作業として決定）
- Scope: MCPの読み取り専用境界、`02_Architecture/api.md`、`03_Implement/mcp/README.md`
- Related: `ADR-0054`（外部接続層の段階導入）、`ADR-0093`（agent資格情報）、`ADR-0103`（単位digest）、Issue #3271、TAI Pleroma issue #67

## 価値への寄与

V3「レビュー」と、SafeMode・proposal-onlyの不変条件に寄与する。外部agentの書込み経路を増やすと、未レビュー入力の取り込み、権限、監査、undoの境界が広がる。具体的な受信契約と運用主体が決まるまで、読み取り専用の境界を維持する。

次の不変条件は緩和しない。

- SafeModeは既定ONのまま。
- AI出力は提案のみで、自動適用しない。
- `human_reviewed` は人間だけが設定する。
- MCPは読み取り専用のままにする。

## Context

ADR-0054の段階2は、webhookから提案カードを取り込み、提案のみを書き込む構想である。MCPは現在、読み取り専用の2ツールだけを持ち、書込み・取り込み・適用・公開の機能を持たない。

TAI Pleroma は、agentの書込みAPIがないことを接続の詰まりとして挙げている。ただし、TAIが求める書込みが提案のingestで足りるのか、カード・島への直接の書込みなのかは、まだ具体化していない。後者は `human_reviewed` の不変条件に反するため、受理しない前提である。

段階2を実装するには、少なくとも次を決める必要がある。

- 受信面の認可（`tenantId + docId` 単位、ingestごとの既存access-control）
- 入力のスキーマと、未レビュー・自動確定なしの扱い
- SafeModeと提案のみの不変条件を、取り込み時と表示時のどちらで強制するか
- 監査（誰が、どの文書に、どの提案を取り込んだか）
- 個別undoと、既存の提案ライフサイクルとの関係

## Decision

段階2の提案ingestは、今は実装しない。必要性と受信契約が具体化するまで、MCPとagent資格情報の書込み面を作らない。

再検討の条件は、次のすべてが揃ったときとする。

1. TAIなどの利用者が、提案のingestで足りる具体的な入力例と頻度を示す。
2. 受信面の認可とテナント境界の設計が、既存のaccess-controlと矛盾しない。
3. SafeMode、提案のみ、`human_reviewed` を、取り込み時と表示時のどちらで強制するかを決める。
4. 監査とundoの単位を決める。
5. 新しいADRで、上記と `api.md` の契約を固定する。

## Consequences

- MCPは読み取り専用のままである。TAIは、既存の利用者資格情報の経路か、人向けの取り込みを使う。
- 段階2を追うIssueは、上の条件が揃うまで作らない。必要になった時点で、このADRを更新するか新しいADRを起こす。
- 提案の版固定は、CE-1の `sourceBundleHash` を使う（#3295 / #3311 の判断）。段階2でも同じ値を使う。
