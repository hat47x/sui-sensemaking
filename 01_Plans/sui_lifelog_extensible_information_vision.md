## 1. 構想の中心：記録を増やすのではなく、自分の情報基盤を育てる

ライフログを「専用アプリが決めた項目へ毎日値を入力すること」に限定しない。生活中の出来事、読んだ文章、未整理のメモ、仕事や研究の試行錯誤、生成AIとの対話、そこから生まれた仮説や設計判断を、時間を経て参照・再解釈できる情報として扱う。

**SUIは情報が生まれる場所を独占しない。** TEI、SHO、AIハーネス、日記、カレンダー、外部アプリ、ファイル、SUI自身など、どこからでも情報を受け入れる。入力時の強制分類や全自動の意味付けより、記録を失わず元の場所へ戻れることを優先する。

記録には三つの見方が重なる。
- **時間の連なり**：出来事、取得、記述、解釈、更新の時点と期間。
- **意味のつながり**：問い、観測、仮説、出典、支持・反証・別解などの関係。
- **情報のまとまり**：同じ経験、研究、生活上の活動、設計検討をまとめるEpisode／Document／KJの島。

それらを横断して、各情報単位へ後から**任意の属性を付け足せる**ことを四つ目の基本能力とする。型・表示・集計が必要になったときだけ拡張すればよく、特定のライフログ分野の入力項目を初めから全利用者へ課さない。

ここでいう「永続」は、サービスやモデルが無限に稼働し続ける保証ではない。**情報の所有、一般的な形式での読取・書出し、参照の持続、モデル移行、部分的な機能喪失時の退避**を設計の中心に置くという意味である。

## 2. AIハーネスのセッションも、ライフログの源泉になる

生成AIとのセッションには、疑問を持った時点、回答や反証、使用した資料、選んだ案、修正した理由、開発・調査の経緯が記録される。外に表れた思考と活動の履歴として、セッションそのものをライフログの一種として扱える。

ただし、**セッション＝人間の内面そのものではない**。セッションに記録された発話・ツール実行と、AIが推測した気分・動機・意図を分離する。記録されていない心情や出来事をAIで補完して事実化しない。

セッションの取り扱いは次の四つを区別する。

| 方式 | 内容 | 保存・公開の扱い |
| --- | --- | --- |
| Live reference | ハーネスの元セッションを権限の範囲で参照 | SUIが全文を複製したとみなさない。アクセス不能時はunavailable |
| Snapshot | 特定の時点に取得できたメッセージ・結果の固定版 | 取得範囲・Revision／Locator・隠した情報を記録する |
| Extract | ユーザーが選んだ発言・問い・結果だけを取り込む | 原文へ戻る参照と抽出時点を保持する |
| Derived document | セッションを基にしたMarkdown、アウトライン、判断の整理 | AIの生成物であることを保持し、原発話と別のDocumentとする |

閲覧上はどの方式もDocumentとして開けるが、実際の正本やSessionの継続・分岐能力はハーネス側に残り得る。ハーネスの会話をSUIが再現しただけで、元のTool実行やSession継続に成功したと主張しない。

**既定では私的な情報源**とし、公開文書、検索結果、バックリンク、Constellation上の星・線・件数、AI送信、ダウンロードに自動混入させない。本文が見えない場合も、存在や関連性だけで漏れることがある。公開用には必要な部分を選んで別Documentを作成し、秘密・資格素材・非公開Sourceを確認する。現行のSafeMode、テナント認可、未レビュー非公開、proposal-only、human_reviewedの境界を変えない。

## 3. Inboxは情報空間の入口であり、整理の義務ではない

Universal Inboxは、どこで生まれた情報でも受け入れられる**統合ビュー**とする。独立した第二の保存正本を当然視しない。

受入単位は次の状態を区別できるようにする。

| 入力の状態 | 保持するもの |
| --- | --- |
| URLだけ | 相対／絶対URL、取得先、登録時点、未取得の事実 |
| 原文Snapshot | 取得済みの実byteまたは保持済みDocumentへの参照、版、取得範囲 |
| 外部のLive reference | Locator、Reader、現在の取得可能性・開示範囲 |
| 自分のQuick Capture | 本文、記録日時、任意の属性、保存先 |
| AIの生成候補 | 元のContext Pack、出力、生成者、未採用状態 |

Inboxでは、後からタグ付けやEpisodeへの追加ができる。意味が未分化な情報、長いRaw本文、URLのみの参照を正常な状態として保持し、無理に既存の分類へ押し込まない。

Quick Captureでは、テキスト欄が直ちに入力可能な小さなウィンドウを想定する。アプリ内の新規文書操作に加え、OS競合を考慮した設定可能なグローバルショートカットを提供する構想とする。保存はタグ推薦やAI分析を待たず、成功を確認してから必要な候補を追加する。

タグは最近利用したもの、近傍Document、共起、既存の用語から高速に推薦し、クリック・キー操作で連続選択できる。AI OFFでも動作する。類義語を大量に新タグ化しない。

## 4. 情報の時間と意味を損なわない

### 4.1 出来事と記録と解釈の時刻を分ける

必要な場合、少なくとも以下を論理的に区別する。

- **occurredAt／period**：出来事が起きた日時・期間。日時が曖昧なら精度も保持する。
- **capturedAt**：SUIや外部ツールが取得した日時。
- **recordedAt**：記録として保存した日時。
- **interpretedAt**：意味付け・仮説・AIによる再解釈を記録した日時。
- **revisedAt／revision**：内容や属性値を変更した日時・版。

出来事・記録・解釈の時刻が異なっても矛盾ではない。「数年前の春」「11月のどこか」などの曖昧な時刻を架空の精密日時に変換しない。予定は実行済みのEventではない。タイムゾーン・夏時間・複数期間を失わない。

### 4.2 Episodeは後から見つけられるまとまり

Episodeは、複数の日・Document・Item・セッションを横断する「ひとつながりの経験・思考のまとまり」である。最初のメモの時点でEpisodeが定義されている必要はない。後からKJ的に形成でき、同じItemが複数Episodeへ属してもよい。

Episodeは固有の新テーブルを先に要しない。まずDocument／Item／Relation／Collectionの組合せで表現し、足りなさを実証してから永続化方式を決める。Episodeの所属を事実の因果や診断と混同しない。

### 4.3 思考の変化を履歴として扱う

原発話・原文、後で見つけた根拠、AIの仮説、人が受理した理解を別々に保持する。新しい理解で過去の原文を置換しない。Journeyは調査の経路、Episodeは情報のまとまりであり、同じものではない。

時間軸・意味的Relation・Episode所属・出典を重ねるビューを持てるようにする。Constellationでは「検索語との関連」「意味的近さ」「明示的なリンク距離」「時間的近接」「Episode共有」を別々に見せ、画面上の距離を確定した因果関係とみなさない。

## 5. 任意の情報単位へ、必要な属性を増やす

### 5.1 構造の固定ではなく、後からの拡張を標準とする

ある日、利用者が生活メモに「気分」と「活動」を記録したくなったとする。SUIの対象を選択し、「属性を追加」から名前、値の種類、選択肢、入力単位を指定すれば、即座に記録できる体験を目指す。

必要なら同じ属性を別のDocument、Item、Episodeに再利用する。何も入力していない既存Documentを遡って無理に埋めず、各Itemに無関係な列を表示しない。

**属性の適用対象を明示する**。
- Documentに属する属性：文書の公開範囲、種類、目的など。
- Itemに属する属性：記録内容や状態、観測値。
- Occurrenceに属する属性：表示位置、特定のビューでの折りたたみなど。
- Relationに属する属性：関係の向き、仮説・支持・依存の根拠。
- Episodeに属する属性：期間、仮題、含まれる記録の役割。

「表示を移動しただけで気分の値が変わる」「あるDocumentの公開範囲をItemの出典と混同する」といった誤配属を防ぐ。

### 5.2 属性定義と値を分離する

概念上、次の関係を使う。

| 概念 | 主な情報 |
| --- | --- |
| Field Definition | 安定した識別子、表示名、適用対象、値型、単位・尺度、候補値、検証条件、定義版 |
| Field Value | 対象ID、Field ID、実際の値、観測時点、元資料、値の改訂、本人入力／AI候補の区別 |
| Field Set / Template | 再利用する属性のまとまり。押し付けず、必要時に適用 |
| View Definition | 入力UI、表、検索、グラフなど、Field Valueの表示と操作 |
| Capability / Operator | 集計・検証・通知・生成などの機能。必要に応じTEI側で拡張 |

上表は**論理設計候補**であり、新しいDB表、ABI、共有型Registryを確定したものではない。現行の[Card.meta](../03_Implement/frontend/src/domain/types.ts)は\`seq\`／\`source\`のみを意図した限定契約で、未知の\`meta\`キーを保存する汎用領域ではない。そこへ自由な属性を押し込んで現行バリデーションを迂回しない。現行DocumentV1を破壊せずに試す別のFixture／Sidecar／Plugin入力などから最小Fit/Gapを検証する。

### 5.3 型と値の意味

最初の基本型候補は、文字列、数値、真偽、日時・期間、列挙／複数選択、タグ、URL、対象参照、Markdown本文、必要なら単位付き数値とする。

集計や検索に使う属性については、値の意味も保持する。
- 未入力／未取得／該当なし／非公開／計測失敗を、\`0\`や\`false\`や空文字と混同しない。
- 単位、尺度、選択肢の定義、ロケール、時間帯、型の版を必要に応じて保持する。
- 値の訂正、再計測、解釈の変更は別の操作とし、元の観測を無断で書換えない。
- 数値から得られた相関候補を、原因や診断へ自動昇格しない。

### 5.4 生活メモへ「気分」「活動」を追加する例

1. メモをInboxへ保存する。最初は本文と出典だけでもよい。
2. 利用者が「気分」を追加し、自己申告の選択式または尺度を定義する。
3. 「活動」を複数選択式として追加し、過去に使った候補から選択する。
4. フィールドを保存した後、日付のタイムラインやEpisodeごとに検索・一覧表示する。
5. 後から選択肢や尺度を変えた場合も、旧値が新尺度の値だったことにはしない。
6. 必要に応じてTEIで入力・集計・検証・可視化の機能を追加し、SUIの元記録へリンクする。

これは一般的な自己観察の例であり、**医療上の診断・治療効果・臨床尺度の妥当性を保証するものではない**。精神的状態などの機微属性では既定の公開・外部送信を抑え、ユーザーに意図を確認する。将来の専用機能は、適切な専門的検証・表示条件を満たすときだけ追加する。

## 6. TEIによって、自分の情報基盤を拡張する

SUIが全専門分野の入力画面・分析アルゴリズム・統計処理を内蔵する必要はない。**基本的な情報の受入・関連付け・表示はSUIが担い、業務／生活分野に固有の能力をTEIでモデル化・生成して追加する**ことを目指す。

機能拡張の段階は次のとおり。
1. **SUI標準**：属性の追加・編集、簡単なフィルタ、タグ候補、一覧。
2. **再利用設定**：Field Set／Template、入力候補、検証ルール、ビュー定義。
3. **TEI生成**：フィールドや入力規則を契約化し、表・フォーム・グラフ・集計・外部連携など必要な専門機能を生成する。
4. **外部実行・連携**：TEIが想定するHostやPluginで機能を実行し、SUIへ結果Documentや値候補を返す。

TEIのDSL要素、Go実装、生成器の内部仕様をSUIの日常入力画面へ露出させない。外部言語は能力を拡大するために使い、単なる日々の入力をプログラミング作業にしない。

TEIが生成した表示や集計をSUIから利用できても、**TEIによるコード生成、外部Hostでの実行、SUIでの記録の正式保存、意味的な受理、AIの再解釈は別々の資格**である。新たなSUI–TEI双方向書込み契約を今回の採用で確定しない。元のField Definitionの版、出典、現在のDisclosure／権限を再照合する。

将来の「無限の拡張」は実装範囲・性能・認可を無限と約束するものではない。**標準機能を改造しなくても、必要な分野の能力を後から増やせる**ことを目標とする。

## 7. 可搬性と長期の生存性

アプリケーションは役割を終え得るが、利用者の記録まで消えてはならない。

- **標準の出口はMarkdown＋相対URL**。文書本文、基本のタグ・日時・平坦な属性にはYAML Frontmatterを利用できる。
- Episodeの多重所属、複数Occurrence、意味Relation、機微情報の開示、Field定義版、履歴など、Markdownだけで損失なく表せない場合は**明示的なSidecarまたは構造化エクスポート**を使う。Markdownだけの完全復元を約束しない。
- 保持先はSUI独自の第二Storeを即座に作るとは限らない。元SourceとSnapshotのどちらが正本か、保存できた／再読できた／現在も参照可能かを別々に確認する。
- 値型・属性名・単位・選択肢の変更時は、版と移行／後方表示の方針を記録する。単なるリネームを値の意味の変更と混同しない。
- 特定のAIモデル、外部サービス、課金、クラウドに依存しなくても、少なくとも記録の閲覧、再検索、リンク追跡、データ書出しは可能にする。
- バックアップ、書出し／再取込み、参照修復、部分破損・未対応Plugin時の読み取り劣化を段階的に実証する。

ObsidianのMarkdown+YAML Properties+Basesは、汎用的な属性と動的ビューを開かれたファイル上に重ねる先例である。ただしSUIでは、属性をDocument以外の情報単位にも適用し、出典・時間・意味と組み合わせる点を深める。

## 8. 検索・Constellationとライフログの統合

検索から得られるものは、正解の文書一件だけではない。時間的に離れた記録、意味が近いメモ、同じEpisodeの別の出典、複数のAIセッションに繰り返し現れた問いが、アイデアの材料になる。

Constellation Viewや検索一覧では、**語句一致、意味的類似、時間近接、リンク距離、Episode共有、属性条件**を区別する。単一スコアに潰す場合も、その根拠と適用範囲を表示する。画面の近さを因果・同一性・正しさの証拠としない。

検索中に生まれた考えはQuick Captureで即座にInboxへ保存する。保存後に検索語・選択Item・現在のDocument／Sourceへリンクし、Context Packからハーネスに関連候補や反例を尋ねる。**保存の成功とAIの分析成功を分離**し、AIが使えなくてもメモを失わない。

検索結果やConstellationのノード・線・件数も現在の開示範囲に従い、非公開セッションの存在を漏らさない。

## 9. 最小の実証順と追加の反例

| 段階 | 最小の縦断 | 成功の上限 |
| --- | --- | --- |
| **R0：現状を確かめる** | 現行DocumentV1の実保存→別Reader再読取、Raw SourceとLocatorの区別、非公開の読取境界 | 既存[#3438](https://github.com/hat47x/sui-sensemaking/issues/3438)などに帰属。今回のDoc更新ではPASSにならない |
| **L1：手動記録の往復** | 外部またはQuick Captureから一件保存→Inbox表示→元URLへ戻る→Markdownで書き出す | 新Store・新権限エンジンを前提にしない |
| **L2：任意属性の付与** | 既存のDocument／Itemに二つの定義済み属性を後付け→別起動で再読→日時・尺度・未入力を保持 | 現行\`Card.meta\`に未知キーを混ぜず、候補の保存境界を明記 |
| **L3：セッションの限定取り込み** | 模擬ハーネスセッションの一部を非公開Snapshot化→引用先を再表示→別Harnessへ無断送信しない | 実セッション接続と模擬Fixtureを混同しない |
| **L4：関連から発想へ** | 異なる日時の三記録→検索・Constellation候補→Episode作成→新しいDocumentへ洞察記録 | 人が新しい関係を実際に発見したかT2で検証 |
| **L5：TEIによる拡張** | L2属性を限定した契約からフォーム／集計機能生成→既存記録へ参照リンク→版・権限を再照合 | 生成コードとSUI正式Writerの実受理を分離 |

**高判別力の負例**：
1. 同文別Source・同Item別Occurrence・同一セッションの再インポートを、理由なく統合・重複計上しない。
2. 検索文書が非公開セッションを参照しても、星・線・件数・自動タグ・外部Context Packから漏らさない。
3. 11月の出来事を翌年に記録し、さらに後で再解釈しても、occurred／recorded／interpretedを一つに書換えない。
4. 未入力・0・該当なし・非公開・取得不能の属性値を区別する。
5. 気分尺度の値域を変更しても、旧値を新尺度で記録したかのように統計処理しない。
6. 一つの記録を複数Episodeへ置いても、元Itemを勝手に複製しない。
7. 属性を削除・改名・型変更した場合も、旧Documentの読み取り、未知の値の退避、変更の監査を考慮する。
8. AIによる分析が途中失敗しても、先に確定したQuick Captureが失われない。
9. 一つのセッションから抽出したDocumentを公開しても、未選択の発言やTool出力を同梱しない。
10. TEI生成フォームの値書込みが失敗・競合した場合、SUI側で成功扱いせず再照合する。
11. Pluginやハーネスが利用不能でも、既存のMarkdown／属性定義／相対URLを読める範囲が失われない。
12. AI OFFでL1、L2、L4の手動の経路が成立する。

新規の大規模実装Issueを一度に起こさない。まず現行DocumentV1とRaw Readerで実現できる範囲を観測し、新しい保存境界・Field Contract・TEI接続が必要であることが独立に確認できてからOwnerへ採否を返す。

## 10. 参考になる既存技術と限界

- [Obsidian Properties](https://obsidian.md/help/properties)：Markdown上のYAML Frontmatterで型付きの属性を保持する。属性がDocument単位・小さな値に適することも確認できる。
- [Obsidian Bases](https://obsidian.md/help/bases)：同じMarkdown群をフィルタやビューで再利用する先例。SUIのLive CollectionやTime／Episodeビューの参考。
- [ActivityWatch](https://docs.activitywatch.net/en/latest/faq.html)：ローカルに記録を保持する自動活動ログの先例。記録の収集と解釈を分ける参考。
- [W3C PROV-O](https://www.w3.org/TR/prov-o/)：Entity／Activity／Agentを区別した来歴の表現。SUIの既存意味モデルやOwner境界を置換するものではない。
- [FHIR Observation](https://hl7.org/fhir/observation-definitions.html)：観測時点、報告時点、値なしの理由などを区別する先例。SUIの生活記録へFHIRを直接導入する決定でも、医学的な適合性の保証でもない。

## 11. 構想の位置付けと覆す条件

本書はSUIが専門分野ごとの固定的なライフログアプリを目指すという意味ではない。**生活や知的活動のどこで生まれた情報も受け止め、時間・意味・まとまり・属性を重ねて再利用し、必要な専門機能をTEIなどで後から足せる**ことを、長期的な製品方向として採録する。

すでに受理されたDocumentV1、既存SaaS認可、SafeMode、ADR-0089の一次価値、外部Producer／Consumerの責務、AI候補のHuman reviewは変えない。新設する概念名やSchemaは、具体的な実装・利用証拠によって、縮小・変更・不採用にできる。

新しい機能が情報の取得・保存・原資料への復帰・人間の洞察形成をかえって難しくする場合には、複雑なモデルより簡潔なMarkdown／URL／手動操作を優先する。
