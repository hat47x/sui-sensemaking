01

分析の枠組みと適用範囲

関数従属性 x → y とは「xの値に対してyの値が一意に対応する」関係を指す。 本分析の主張は単純である。同一の関数従属性を複数箇所に保持すると、 それらを一致させる仕組みが存在しない限り、読み取り側は推測せざるを得なくなる。

DocumentV1 は単一JSONスナップショットであり、物理DBの外部キー制約を持たない （documents.payload_json は不透明なTEXT）。したがって整合性を保つ手段は 検証コード（validate_doc.ts）の不変条件だけである。 この前提は変えない。ローカルファーストと単一ファイル可搬性はアーキテクチャの目標であり、 物理正規化はその目標と衝突する。

1.1 適用範囲の線引き

領域適用理由
統合関係、島所属、辺の端点、レビュー帰属、判断ログ、テナント/利用者対応適用するシステム内世界の確定事実。「統合されたか否か」は解釈ではなく事実であり、関数従属性が実在する
text / summaryText / critique適用しない内容は正規化の対象ではない。言葉を選び直すこと自体がKJ法の作業
x / y（空間配置）適用しないKJ法において配置は意味である。正規形の概念が適用できない
claimType / holdState / critiqueTags適用しない利用者の現在の見立て。可逆であり、確定を意図しない

この線引きから得られた対比軸である「確定事実」と「現在の見立て」は、本分析の範囲を超えて SafeModeのredact判定、エクスポートの既定のONとOFF、L0〜L3の割当根拠にも適用できる余地がある。本書では指摘にとどめる。

F-3 統合関係が4フィールド・2実装に分散

検証済み

「N枚のカードを1枚へ統合した」というドメイン関係は一つである。しかし現行の実装では、 2つの関数が、排他的なフィールド集合で、同じ関係を書いている。

書き込む対象 applyCanonicalization()
domain/canonical_ops.ts		 createRepresentativeMerge()
domain/representative_merge.ts
新カード（統合先）へsources: string[]repOf: string[]
元カード（統合元）へcanonicalId: stringmergedIntoCardId: string
島の更新元カードを残したまま統合先を追加rewire 指定時のみ元カードを除去して統合先を追加

結果として同一のドメイン事象が、2種類の構造的に異なる文書状態を生む。 どちらの経路を通ったかは、どのフィールドが埋まっているかからしか判別できない。

挙動差は保持すべき仕様である。 applyCanonicalization() が元カードを島に残すのは、 「代表カードと出典カードを両方たどれる」というsui-sensemaking固有の設計 （isSourceCard()、出典カードの開示UI）に基づく。 したがって是正の方向は2つの挙動を1つに統合することではなく、 関係の重複だけを解消して挙動差を明示的な属性にすることである。

F-4 解決経路が固定値で返る

潜在（未露出）

resolveRepresentativeOriginTrace() は統合元IDを次の3経路から収集する。 すなわち、repOf、mergedIntoCardId の逆引き走査、sources である。 ところが、返り値の representativeResolvedBy を 経路によらず "repOf" に固定している。 

// domain/merge_traceability.ts

  if (representative?.repOf && representative.repOf.length > 0) { ... }      // 経路1
  for (const card of document.cards) {
    if (card.mergedIntoCardId === representativeCardId) { ... }               // 経路2
  }
  if (representative && sourceIds.size === 0 && Array.isArray(representative.sources)) { ... }  // 経路3

  return {
    representativeCardId,
    sourceCardIds,
    missingSourceCardIds,
    representativeResolvedBy: "repOf",   // ← 経路2・経路3で解決しても "repOf" と報告される
  };
呼び出し経路影響状態
resolveDecisionOriginTrace() 経由影響なし呼び出し側が実際の解決経路で上書きするため、正しい値が返る
App.tsx からの直接呼び出し誤った来歴を返す現時点では呼び出し側が sourceCardIds / missingSourceCardIds のみを使用し、representativeResolvedBy を参照していないため未露出。この値を使う変更が入った時点で顕在化する

単体テストは toEqual で固定値 "repOf" を期待しているため、この不整合を検出しない （merge_traceability.test.ts）。F-3を是正すれば本項は構造的に消滅する。 是正しない場合は、返り値を実際の経路に合わせる単独修正が必要。

04

F-5 島所属の関数従属性が強制されていない

構造

App.tsx はカードから島を引くとき islands.find(i => i.cardIds.includes(cardId)) で、最初に一致した島を採用している。これは cardId → islandId を関数（一意）とみなす実装である。 しかし Island.cardIds[] は逆方向の配列であり、 同一カードが複数の島に列挙されていてもstrict検証は通過する。 関係が「島 → カード群」の形で保持されているため、「カード → 島」の一意性を表現できていない。

4.1 既存の一意制約は手書きで、対象が非対称

複合キー相当の一意制約は、既に一部の関係で手実装されている。ただし対象が揃っていない。

関係一意性の扱い実装箇所
evidenceLinksあり。(fromCardId, toCardId, type) の重複を検出するvalidate_doc.ts / validate.ts
shelfあり。cardId の重複を検出するvalidate_doc.ts
島所属 (islandId, cardId)なし。島をまたぐ重複を検出しないなし
統合関係 (統合先, 統合元)なし。4フィールド間の一致も検証しないなし

一意制約が必要であること自体は既に認識され実装されている。欠けているのはどの関係に必要かを 体系的に判定する手順であり、個別の実装力ではない。

05

F-6 イベントログが状態から導出されている

構造

sui-sensemakingには統合判断のイベント記録が既に存在する。 それは DocumentV1.mergeSuggestionDecisions[] と物理テーブル merge_decision_logs である。 ところが domain/merge_decision_audit.ts は、監査イベントを作るために resolveDecisionOriginTrace() を呼び、カード側に散らばった状態から 来歴を再構成している。依存が逆転している。

なお「追記のみ」を全モデルへ広げる主張ではない。不変であるべきは 確定した事象（統合判断、レビュー帰属、RoundSnapshotV1）であり、 作業中の DocumentV1 は可変のままでよい。現行の DocumentV1（可変）と RoundSnapshotV1（不変）の分離はこの区別と整合している。

06

F-7 機能単位の追加が構造を発散させている

構造

DocumentV1 は21フィールドを持ち、うち12が省略可能である。 省略可能なフィールドの多くは、機能issueが1件ずつ追加した経緯を持つ （shelf ← DOMAIN-EXPR-02、contradictionSignalDecisions ← DOMAIN-EXPR-04、 ka ← DOMAIN-KA-01、meta ← DOMAIN-TRACE-01、 representativeCue ← DOMAIN-VISUAL-CUE-01）。

これは設計の失敗ではなく、採用している手順の必然的な帰結である。 機能から出発すると、その機能が必要とする最小のフィールドが追加される。 関係から出発した場合と違い、既存の関係と統合されるかどうかは検討の対象にならない。 F-3はまさにこの形で生じた。2つの機能issueが、同じ関係を、互いを知らずに実装した。

ADR-0058（単一 DocumentV1・追加のみ）は バージョンの分裂という別の失敗を正しく防いでいる。 ただし「追加のみ」は構造の縮約経路を持たないため、 関係の重複を検出する手順を伴わない限り、発散は単調に進む。 本書が提案するのはADR-0058の撤回ではなく、その手前に 「新しい省略可能フィールドを足す前に、既存の関係と重複しないかを確認する」 という一段を挟むことである。

07

是正案（初稿）

物理DBの正規化は行わない。ローカルファーストと単一JSON可搬性を壊すため、 適用範囲を「文書内の論理不変条件」に限定する。以下は初稿であり、§08でより厳密に精査した 結果に更新されている。最終判断は§08を参照すること。

段内容対応する所見破壊的変更
R1 resolveRepresentativeOriginTrace() の返り値を実際の解決経路に合わせる F-4 のみ なし。単独で実施可能。スキーマ不変
R2 関数従属性の不変条件を validate_doc.ts へ追加する。対象は 島所属 (islandId, cardId) の島をまたぐ重複、 統合関係4フィールドの相互一致である F-5、F-3の検出 なし（検証強化のみ）。ただし既存文書が新規則で不合格になり得るため、 警告の段階を先行させる判断が要る

4観点分析と検証（2026-08-08）

§07 は単独の分析による初稿である。データモデリング判断は開発が進むほど不可逆になるため、 「今すぐ全部直す」か「当面据え置く」かの二択ではなく、どの範囲を・いつ・どの強度で 構造化するかという配分判断こそが本題である。この配分判断を、独立した4つの観点 （データ整合性、ローカルファーストとJSON可搬性、可逆性と移行コスト、KJ法ドメインへの適合） から並行して再評価し、統合し、統合結果を検証した （§07の対案をそのまま受け入れず、各所見の再現性をコードから再確認する形で行った）。

8.3 先延ばしコストによる優先順位

「緊急度」とは独立に、「先延ばしにするほど1機能追加あたりのコストがどれだけ増えるか」で順序づける。 統合過程の中間結果に含まれていた「R2(a)は§B（階層サブ島）の実装に構造的に必要」という根拠は、 本書執筆者がADR-0007を確認した結果、誤りと判明したため削除した （§Bに対応するFB-RM-MID-04は2026-03-01に完了済みで、使用しているのは 島同士の親子関係parentIslandIdであり、カード→島の一意性とは無関係）。

  1. R3-tier-2は、本分析で唯一「先延ばしにより遡及不能な情報損失が生じる」候補である。ログ導入前の統合は、永久に後から補完できない。
  2. R2(a)書込み側バグは、通常のドラッグ操作で今日も再現し続けている。放置期間分だけ違反を含む文書が蓄積する。
  3. R1は、単体では平常時コストは低いが、R3-tier-1着手の直前に必ず先行させる必要がある（条件付きだが差し迫っている）。
  4. R4は、types.tsへの変更頻度（実測約51コミット/5.5か月）に比例して価値が複利的に高まる。R3-tier-2が新フィールドを追加する前に導入すべき。
  5. R5は、実施コストは一定だが、未実施の間もF-3型の重複が機能issueごとに蓄積し続ける。
  6. R2(b)（狭めた版）、新規のtitleReviewed陳腐化、F-8は、修正コスト自体は一定だが、正しさの欠落は未修正の期間分だけ蓄積する。
  7. R3-tier-3とMergeSuggestionDecisionEntryの二重命名は、コストが時間で増加しない（前者は優先順位フラグ、後者は書込み元が単一の間は無害）。急ぐ理由がない。

9.1 本分析が到達していない範囲

9.2 参照した外部知見

関数従属性・定義域制約・複合キーの観点、および「追記のみの記録を正本とし可変な集計を導出する」構成は、 渡辺幸三による業務システム設計の一連の論考（ブログ「設計者の発言」、 情報システム学会メールマガジン2022.10.28 No.17-07「『データ・ファースト』な設計スタイルを身につけよう」、 三要素分析法）を参照した。

ただし当該体系は業務システムの物理DB設計を前提とする。 sui-sensemakingはローカルファーストの単一JSON永続化を目標に持つため、 物理正規化・複合主キーの主張はそのまま適用せず、 論理不変条件の設計としてのみ採用した（§07冒頭）。 またカード本文・空間配置・見立てへは適用しない（§1.1）。 複合キーの適合範囲は原則としてRDBのマスタデータ層の議論であり、単一JSON可搬性を 犠牲にしてまで持ち込むものではない。この判断は§08の4観点分析でも一貫して維持された。
