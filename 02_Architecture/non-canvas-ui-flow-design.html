キャンバス外UIフロー設計

区分: 設計ビュー / 更新: 2026-08-08
正本は各ADR、api.md、schemas.md、master-data-settings-ui-ux-concept.md。 本書はキャンバス外の全画面を業務設計・データ設計・機能設計の三者牽制関係を通して構造化した設計ビューであり、 内容が正本と食い違う場合は正本を優先する。

本書の目的: KJ法キャンバス（カード配置・島形成・関係線・保留操作）を除く全UIフローについて、 「なぜその画面が必要か（業務）」「何を扱い何を扱わないか（データ）」「どのAPI/契約で実現するか（機能）」の 三者が相互に牽制し合う構造を可視化する。単独の次元から画面を正当化せず、三者が揃わない画面は設計しない。

牽制の実践: 各画面の設計判断は、3つの問いに答えられなければ着工しない。
① 業務: この画面がないと、どの利用者ジャーニーが完遂できないか。
② データ: この画面が扱うデータの正本はどこか。本文・タイトルを表示しない原則を侵さないか。
③ 機能: 必要なAPI契約は確定済みか。capabilityの検証経路は存在するか。

3. G1: 入口・文書 グループ

3.1 三者牽制マトリクス

業務設計

  • 利用者: Standard user（認証済み）
  • 目的: 作業対象の文書を見つけて開く。新規作成・サンプル・ファイル取込で文書を開始する
  • ジャーニー: 起動 → 開始パネル（新規/サンプル/再開/取込）→ キャンバス
  • 摩擦（記録済み）: 再読込後に直前文書へ自動復帰しない（dogfood-log-2026-07-10）
  • 非目標: 文書削除・アーカイブ・所有者移管・一括操作・本文プレビュー

データ設計

  • 正本: サーバー GET /docs（id, title, updatedAt のみ）
  • 境界クラス: L1 Supported（文書インデックス）
  • 表示する情報: title, updatedAt（相対/ローカライズ）, id（補助）
  • 表示しない情報: 本文抜粋、カード数、レビュー状態、サムネイル、payload_json
  • 端末キャッシュ: localStorageの「最近」は表示順補助のみ。サーバー確認失敗時はキャッシュから候補表示しない

機能設計

  • API: GET /docs（認可済み射影）、文書を開く操作は GET /docs/{doc_id}
  • capability: document.read
  • 状態遷移: Loading (skeleton) → Empty/Ready/ACL不達/Network error/Read-only
  • 契約状態: GET /docs のapi.md/schemas.md契約は未固定（Round 8 R8-A入力済み、実装未着手）
  • 置換対象: 現行StartPanelの「最近のドキュメント」ダイアログ

3.3 文書一覧ダイアログの状態設計

状態表示利用者操作データ牽制
Loading 行の形を保つ骨組み表示（skeleton）。前回キャッシュの実データは表示しない なし（操作不能） キャッシュからの候補表示禁止（データ設計§2）
Empty 「アクセスできるドキュメントはありません」＋新規作成・ファイル取込への導線 新規作成、ファイルから読み込み 権限不足のEmptyと区別（0件≠権限なし）
Ready タイトル中心の一覧。ID補助表示。現在開いている文書には「開いています」を静的に表示する 行を選択して開く、タイトル/IDで絞り込む 本文・カード数・サムネイル非表示
ACL不達/403 「確認できないため表示しない」＋再試行。キャッシュへの代替表示はしない 再試行 空偽装禁止（データ設計§2 Empty≠権限不足）
Network error 「認可済み一覧を確認できない」＋再試行＋ファイル取込導線 再試行、ファイルから読み込み キャッシュへの代替表示を禁止
Read-only 開くことは可能。新規作成・タイトル変更は非表示にするか、無効化して理由を表示する 開く 書き込めないことを視覚とテキストの両方で説明
三者牽制ポイント: 「文書一覧にタイトルを出す」という業務上の当然の要求に対し、データ設計は 「タイトルはDocumentスナップショットの一部であり、一覧APIは id/title/updatedAt のみを返す」 と境界を引き、機能設計は「一覧だけを使った背後の全文書PUT（タイトル変更）は許可しない」と制約する。 タイトル変更は文書を開いた編集文脈でのみ行う。→ 一覧のインライン編集は三者が揃わないため提供しない。

4. G2: 共有・出力 グループ

4.1 三者牽制マトリクス

業務設計

  • 利用者: Standard user（文書を開いている状態）
  • 目的: 文書の内容を、確認可能な形で他者と共有する
  • ジャーニー: キャンバス → 共有と再現パネル → 共有前確認 → 出力形式選択 → 書き出し
  • 必須確認: SafeModeチェック、公開範囲確認、未レビュー情報の扱い、出力形式、レビューパック粒度
  • 非目標: 共有URL発行、リアルタイム共同編集、公開先ディレクトリ管理

データ設計

  • 正本: Documentスナップショット（payload_json）
  • 出力に含む: レビュー済みカード・島・関係。SafeMode ON時は未レビュー除外
  • 出力に含まない: SafeMode ON時の未レビュー本文、出典参照の生URL（設定による）
  • 出力形式: document.json, view.json, abstract map, canvas PNG/SVG, レビューパック
  • 共有範囲: 出力ファイルの受け渡し。サーバー媒介の共有機能は持たない

機能設計

  • API: 出力はすべてクライアント側で生成（export/ モジュール）
  • 契約: document.json/view.json形式はschemas.mdで固定
  • 状態遷移: 共有前確認（SafeMode/公開範囲/未レビュー/形式）→ プレビュー → 出力実行
  • 安全: SafeMode ON時は未レビュー情報の自動除外、共有前の明示確認必須
  • 実装状態: 共有前確認パネル・エクスポート機能とも実装済み

5. G3: AI・提案 グループ

5.1 三者牽制マトリクス

業務設計

  • 利用者: Standard user（AI提案を補助として使う）
  • 目的: AIが生成した候補（島ラベル・関係・カード分類・矛盾検出・文書タイトル）を人間が審査し、採用/棄却する
  • ジャーニー: キャンバス → AI提案パネル → 提案ごとのレビュー → Adopt/Reject
  • 鉄則: AIは候補生成に留まり、確定しない。人間の明示操作なしに文書へ反映されない
  • 非目標: 一括Adopt/Reject、スコアリング、AIの自律実行、チャットUI

データ設計

  • 正本: AI提案は派生データ（L3 Derived）。文書本体には人間がAdoptした結果のみ残る
  • 提案構造: 提案の種別・対象ラベル・内容・根拠・差分（該当する場合）
  • 表示する情報: 提案内容、根拠、影響範囲、競合の有無
  • 表示しない情報: score/rank/confidence（反スコアリング）、AIの内部状態
  • エージェント応答: agent-response.v1互換のペイロード。未レビューの提案カードとしてのみ取り込まれる

機能設計

  • API: POST /ai/*（提案生成）、提案のAdopt/Rejectはクライアント側で文書の差分として適用
  • capability: document.write（Adopt時）
  • 状態遷移: 提案一覧 → 提案ごとの詳細 → Adopt確認 → 適用/棄却
  • 安全: proposal-only、SafeMode ON時はAI提案の出典参照を秘匿、人間の明示Adoptのみ
  • 実装状態: SuggestionPanel, MergeSuggestionsPanel, PatchWorkspacePanel 実装済み

三者牽制ポイント: 業務上「AI提案を一括で採用したい」という要求が生じうるが、データ設計は 「各提案は独立した根拠と影響範囲を持ち、相互に競合しうる」とし、機能設計は「提案ごとの明示的なAdoptのみ。 一括操作は提供しない」と制約する。また、patchSignatureMismatch時はアプリ内での適用を拒否し、パッチ書出に留める （データの整合性を機能が守る）。エージェント応答のうち、対象を解決できない提案（orphaned）はAdoptできない。

6. G4: 高度作業 グループ

6.1 三者牽制マトリクス

業務設計

  • ナラティブ（B型叙述）: 空間配置から文章化し、A型図と照合する
  • 保留棚卸し: 保留・未決・棚上げ状態のカードを一覧し、状態変更または対処する
  • 探求ジャーニー（W型）: R1（問題提起）→R2（現状把握）→R3（本質追求）→R4（構想）→R5（具体策）→R6（手順）の累積的KJ法
  • 利用者: Standard user（キャンバス作業の延長として使う）
  • 表示: 既定OFF。「詳細」ONの作業モード面として段階開示

データ設計

  • ナラティブ: Document内埋め込み（L2 Embedded-only）。個別CRUDなし
  • 保留棚: Card.holdState（"hold"/"undecided"/"shelved"）をDocument内から抽出したビュー
  • 探求ジャーニー: RoundSnapshot DAGとしてDocument内埋め込み。InquiryBundle（L1.5 Append-read）
  • 表示する情報: ナラティブ本文、保留カードの一覧と状態、ラウンド間の系譜
  • 表示しない情報: スコア、準備度、進捗率、完了判定

機能設計

  • API: ナラティブ・保留棚はクライアント側のdocument内データ操作のみ
  • 探求ジャーニー: POST /context/bundles:resolve（コンテキスト投影）
  • 状態: 各作業モードは独立した開閉状態。キャンバス選択とは分離
  • 実装状態: NarrativesPanel, ShelfPanel 実装済み。InquiryJourneyPrototypePanel 試作

7. G5: 管理面 グループ（本文非表示・メタデータ識別）

7.1 管理面全体の設計根拠

管理面の基本原則（2026-08-08 補正）: 管理面はキャンバス（本文を扱う面）とは別サーフェスとし、 「この画面は文書本文（カード・島・ナラティブ）を表示しません」という境界説明を常に置く。 識別メタデータ（タイトル・docId・updatedAt）は表示してよい。 カード・ナラティブ・レビュー状態・件数集計は表示しない。 capabilityが不足している場合は該当面を提供せず、APIも安全側で拒否する。
補正根拠: 「本文非表示」原則の「本文」定義が広すぎた。 タイトルは索引情報であり、カードやナラティブのような知的成果物の本体ではない。 管理面でdocIdのみを表示する運用は文書数が増えると破綻し、 誤った文書への設定変更リスクを高める。 タイトル表示による識別精度の向上は、安全上の利益が損失を上回る。 詳細は admin-surface-metadata-display-correction.html を参照。

7.2 三者牽制マトリクス（管理面全体）

業務設計

  • アクセス登録（現行）: Platform operatorが新規利用者のidentityをstrict provisioningで登録する
  • 文書アクセス設定（将来のSaaS）: Tenant Adminが有効なテナントの文書の公開範囲とポリシーを管理する
  • エージェント登録（将来）: Tenant Adminが外部エージェントのトークンを発行・失効する
  • システム状態（将来候補）: Platform operatorがプロバイダの状態等を読み取り専用で確認する
  • 監査（将来）: Security/Audit operatorが許可リスト内のメタデータを確認する

データ設計

  • 正本: サーバー（users, user_identities, document_access_metadata, エージェント登録）
  • 表示（識別メタデータ）: 文書タイトル、docId、updatedAt、identity情報（provider, external UID, display name）、公開範囲、紐付け状態
  • 非表示（知的成果物本体）: カード本文・島構造・関係線・ナラティブ・レビュー状態・未レビュー情報・証跡リンク・件数集計
  • トークン: 作成直後の完了面で一度だけ表示。平文再表示・伏字・検索はしない
  • 監査: DATA-MAINT-04が解禁されるまで表示しない（許可リスト未定義）

機能設計

  • API: POST /admin/provision/users, GET/PUT /tenant-admin/document-access
  • capability: 面ごとに独立（document.policy.manage と membership.provision は相互に暗黙付与しない）
  • 実装ゲート: アクセス登録UIは認可主体固定待ち、文書アクセス設定UIはtrusted auth edge接続待ち、エージェント登録UIはEXT-CONN-02契約待ち、監査UIはDATA-MAINT-04判断待ち
  • SaaS: Tenant Admin / Platform Control Plane / Workspaceの3面をルート・見出し・パンくずで分離

8. G6: Session・Tenant グループ

8.1 三者牽制マトリクス

業務設計

  • 利用者: 全利用者（認証前）
  • 目的: 認証でidentityを確立し、操作できるテナントのscopeを確定する
  • ジャーニー: アプリ起動 → session bootstrap → 認証（必要な場合）→ テナント選択（メンバーシップが複数の場合）→ Workspace
  • テナント切替: セッション単位で有効なテナントは1つ。切替時は全タブへ影響し、未保存の確認を行い、旧scopeを完全に破棄する
  • 異常時: メンバーシップの失効、テナントの不一致、PDPへ到達できない場合はblocked state（本文非表示・再確認導線）

データ設計

  • 正本: サーバー（session context, tenant membership, capabilities）
  • session情報: principal, active tenant, memberships, capabilities, tenantSessionVersion
  • 非表示: raw error, capability名, role/group, policyRef, tenant/principal ID（blocked stateで内容を反射させないため）
  • 端末: テナント単位のlocalStorage。切替時に旧scopeを完全に削除する
  • タブ間: BroadcastChannelは補助。ペイロードにtenant ID, principal, version, title, 本文を含めない

機能設計

  • API: GET /session/bootstrap-policy, GET /session/context, POST /session/active-tenant
  • guard: tenantSessionVersionによる古いリクエストの防止。409時は全面blocked state
  • 状態: Bootstrap → Session解決 → Tenant選択（複数時）→ Workspace / Blocked
  • 実装状態: フロントエンドのsession bootstrap、テナント切替UI、blocked stateは実装済み。trusted auth edgeのバックエンド接続待ちのため、SaaSプロファイルは起動を拒否している

12. 検証観点（三者牽制の完全性チェック）

  • 業務→データ: 各画面が扱うデータの正本は明確か。本文・タイトルを表示しない原則を侵す画面はないか。
  • データ→機能: 保存範囲（サーバー/文書内/端末のみ/環境変数）とAPIの対応は取れているか。境界クラスL1〜L0と実装状態は一致するか。
  • 機能→業務: 必要なAPI契約が未確定のまま画面設計を進めていないか。capabilityの検証経路は存在するか。
  • 業務→機能: 業務要求が未契約APIを暗黙に前提としていないか。
  • データ→業務: 表示要求がデータ非表示原則を侵していないか（管理面での本文表示、一覧でのタイトル編集など）。
  • 機能→データ: APIの有無がデータ境界クラスを歪めていないか（APIがあるからL1運用可能、と誤認させていないか）。
  • 横断: Standard userにAdmin入口が見えない。Admin面で本文が漏れない。テナント越境がない。琥珀色（amber）が保留・違和感以外に使われていない。
