sui-sensemaking ・ Architecture ・ 正本

全体アーキテクチャ

sui-sensemakingの構成要素、責務の境界、デプロイの形態を定義する。上位の文書（README、00_Prompt、01_Plans）を前提とし、思想や要件は足さずに、実装できる構造に落とし込む。最小のMVPは、Phase 0〜3を主な対象とし、AIは後から付けられる境界だけを先に定義する。

責務境界の正本 型はschemas.md ／ エンドポイントはapi.md

01

アーキテクチャの目標

目標想定採る手段
ポータビリティインターネット上の一般環境／企業・行政のイントラネット／自前ホスティング（オンプレ・仮想マシン）Docker（Compose）で完結する構成を最優先で扱う
低コストでのスモールスタートローカルで完結した検証（SQLite）／小規模運用（PostgreSQL）DBは SQLite ⇄ PostgreSQL を切り替えられるようにする

1.4 プロダクト価値実現の責務境界

製品にするには、機能があるだけでは足りず、利用者が価値を受け取る流れを、構造として支える必要がある。価値を実現するループの正本は value_traceability.md と ADR-0032 とし、本書では責務の境界だけを固定する。

要素固定する責務境界
Frontend開始、カード化、保留と違和感の記録、選択コンテキスト、共有前の確認を、利用者の主要な導線として扱う
Backend保存、検証、ContextBundle、proposal、監査イベントを扱う。ただし、AIの提案の自動確定や、human_reviewed の自動昇格は行わない
DB作業状態、表示状態、レビュー状態、共有用のメタデータを、元に戻せない形で混在させず、共有時に削除や抑制ができる境界を保つ
AI連携任意機能であり、SUI_LLM_PROVIDER=none の既定の構成でも、開始、外在化、構造化、共有前の確認という主要な価値が成立する
共有とエクスポート単なるファイル出力ではなく、確定した点、保留した点、未レビューの情報、根拠への戻り方を、安全に伝える成果物にする責務を持つ

2.1 デプロイ形態

最優先はDocker Compose（推奨）である。web（静的配信、Nginxなど）、api（FastAPI）、db（PostgreSQL）で構成し、必要に応じて ai を追加する。クラウドへの移行（Cloud Run、ECS、低価格のVMなど）は、コンテナの境界を保つことで、運用先に依存しない。

2.2 永続化と切替方針

MVPの永続化は、細かい論理エンティティをすべて正規化する設計ではない。文書の本体はスナップショットとして保存し、補助ログや認証主体の対応表だけを別のテーブルで扱う。物理ER、論理ER、CRUDの可否、関係者ごとの保守責任は data_model_operations_overview.html を正本とする。

接続先は設定ファイルか環境変数で切り替える（SUI_DATABASE_URL=sqlite+aiosqlite:///... / postgresql+asyncpg://...）。DBへの依存はAPI層の末端に隔離し、上位のユースケースはDBの種類を意識しない。

03

APIのI/F方針（MVP）

MVPでは、差分同期ではなく文書のスナップショット保存を基本とする。カード数が百数十程度なら、実装もデバッグも簡単で、必要になればパッチ（差分）を後から追加できる。

エンドポイント備考
GET /docs/{doc_id}なし
PUT /docs/{doc_id}スナップショット保存。現行MVPでは存在しないIDへのPUTを作成として扱う
POST /docsサーバーが採番する新規作成の候補。MVPでは必須ではなく、実装の契約にするのは DATA-CONTRACT-01 で扱う

認証と共有の詳細は、文書保存のAPIとは分けて enterprise_architecture.html、review_attribution.md、共有とエクスポートに関する仕様で扱う。

04

LLM連携（プロバイダの抽象化）

目的は、外部APIへの依存を前提にせず、イントラ内のローカルLLMを使えるようにすることである。LLMProvider は「どのLLMを呼び出すか」を隠す。MVPでは、プロバイダの抽象化の枠だけを用意し、実装は最小でよい。

選択は環境変数で行う。SUI_LLM_PROVIDER=none|local|local_http|large-scale|large_scale|external、SUI_LOCAL_LLM_BASE_URL、SUI_LOCAL_LLM_MODEL、SUI_LLM_ESCALATION_ENABLED=false（既定）。

代表視覚手掛かりは、生成AIだけに依存しない。標準のKJ法の手描きシンボルにつながる基本の描画と利用者の画像、通信が不要な絵文字と同梱のプリセット、権利を確認した外部素材、proposal-onlyの画像生成を、別の経路とする。写真や図が観察データである場合は、識別用の手掛かりではなく、一次の視覚資料として元の文脈を保つ。意味の境界と段階的な導入は 00_Prompt/representative_visual_cue_requirements.md、供給と保存の判断は ADR-0060 を参照する。現行のMVPに、画像生成のAPIや永続の契約が実装済みであることを示すものではない。

05

CE-0 責務・信頼境界

Consensus / Working Repositioning

CEフェーズの開始時点での最小の契約として、Graphの責務、I/O、禁止事項を固定する（対象は責務の境界のみ。API/CLI/UIの実装の詳細はCE-1以降）。

5.1 責務境界とContract ID

Contract ID責務境界
CE0-CTX-IFContextQueryとContextBundleの安全境界、Query Previewを必須とする経路、決定論的なbundleの生成。具体的なキーは schemas.md を参照
CE0-SAFEMODE-IFsafeModeは既定でON、allowUnreviewedText=false が既定、未レビューの本文を保護する
CE0-REVIEW-IFunreviewed / human_reviewed の遷移の境界（昇格は人手のみ）
CG-01..05Working、ContextProjection、Consensusを分離する。patch + approval のみを使う。proposal-onlyとする。監査の4点セットを必須とする

5.2 入出力境界

区分内容
入力（許可）KJ構造（card / island / relation / pending）とquery constraints（scope / depth / reviewFilter / safeModePolicy）
出力（許可）決定論的な bundleHash を持つContextBundle ／ proposalId + diff + rationale を満たすPatch Proposal
適用経路Working → Consensus は applyPatch の承認経路だけを使う。Working → ContextProjection は読み取り専用の投影だけを使う（永続化する更新はしない）

5.3 禁止事項（退行の防止）

  • AIは ConsensusGraph を直接更新してはならない。
  • human_reviewed 状態をAIが自動付与してはならない。
  • safeModeが既定でONのとき、未レビューの本文をAIの入力に含めてはならない。
  • mode=autonomous でもproposal-onlyを維持する。監査の4点セット（query / bundle / proposal / apply）が欠けている場合は、失敗として扱う。
  • Core Graph を契約の語彙に再び導入してはならない（履歴の注記としてだけ許可する）。 検証は DC-VOCAB-001 が行う。

5.4 Go/NoGo Key（実装に着手するためのゲート）

Go条件

  • Query Previewを必須の経路として維持する
  • Working → Consensus の更新経路は patch + approval だけにする
  • mode=autonomous でもproposal-only（自動適用の禁止）を維持する

No-Go条件

  • Query Previewを迂回できる導線がある
  • ConsensusGraph への直接の書き込みを許す導線がある
  • AIだけで human_reviewed へ遷移させる
  • safeModeの既定ON、または allowUnreviewedText=false の既定を後退させる

No-Goの判定は、次の正規のIDを正本とする。正規のIDと異なる表記は、同義語として扱う場合に限って認める。preview_bypass ／ consensus_direct_write ／ auto_apply_or_publish ／ ai_review_auto_promotion ／ safemode_default_relaxation。

5.5 CDCの固定とドリフト停止

  • CE0とCE1のContract IDは、参照専用の固定値として扱い、再採番と異なる意味での定義を禁止する。Contract IDの衝突は0件で固定する。
  • CE1、CE2、CE4は、モックのI/Fを前提に、依存先を待たずに検証を続ける。
  • 本節の契約は責務の境界だけを扱い、推測で実装の要件（APIの詳細、CLI、UIの具体）を追加しない。
  • 語彙の衝突は0件で固定する（契約の語彙は ConsensusGraph / WorkingGraph / ContextProjectionGraph に統一する）。
  • 検証での自己修復は最大3回とする。4回目に相当する時点で停止し、推測で続けることを禁止する。

インターフェース契約の参照先　本書は、型シグネチャ、必須キーとオプションキー、エンドポイント、ステータス、エラーを再定義しない。型、キー、列挙、バージョンの互換はschemas.md §1.2、エンドポイント、認証、ステータス、エラー、副作用はapi.md §2.7〜§2.9、CE1 v1のlogical、transport、handoffの所属はschemas.md layer ownership matrixを参照する。旧Interface Freezeの型、メソッド、イベント順序の再掲と、CE0の入力スナップショットの識別子は形成履歴 へ移した。

07

セキュリティ、可視性、認証の境界

7.1 セキュリティとコンプライアンス（最小の方針）

MVPでは、高度な権限管理は後回しにする。ただしイントラでの利用を想定し、外部サービスとの共有（LLMを含む）は設定で無効にでき、LLMの接続先は明示的に設定する（既定では外部サービスにデータを渡さない）。strict modeの例外承認フローは strict_mode_exception_approval_flow.html を正本とする。

7.2 公開とアクセスの可視性メタデータ FB-RM-PUB-01

公開パック（packs/index.json）とビューのメタデータ（view.json）は、共通の visibility の列挙値 "Public" | "Unlisted" | "Org" | "Restricted" を持つ。

  • 旧 view.json で visibility が未設定のときは、Restricted として解釈する。
  • 旧 packs/index.json で visibility が未設定のときは、Public として解釈する。
  • visibility は表示と配布のメタデータであり、MVPの時点では、RBACの判定ロジックを担わない。
  • SafeModeの既定ONと、共有とエクスポートでの漏えいを防ぐ方針を優先し、visibility の導入によって既存の安全制御を弱めない。

7.3 AuthContext、JIT、strictの境界 AUTH-ARCH-01

  • 認証の境界の正本は ADR-0020 とし、実装の契約は schemas.md、api.md、review_attribution.md の間で、同じ論点について同期する。
  • SUI_ALLOW_JIT_PROVISIONING=true では、未登録のサブジェクトをJITで users と user_identities に作成する。false では 403 で拒否し、事前のプロビジョニングの導線へ誘導する。
  • 帰属の正規のキーは users.id で、外部のサブジェクトは user_identities でのみ解決する。

7.4 SAAS-TENANT-01の境界 ADR-0059・現存する面は実装済み

  • 現行 local-dev / evaluation / enterprise-production はシングルテナントに相当するものとし、共有のSaaSとしては運用しない。
  • 独立したプロファイルの saas-multitenant では、AuthContextに加えて、検証済みのTenantContextと有効なTenantMembershipを、リクエストごとに必ず解決する。不完全なデプロイの構成は、起動前に拒否する。
  • テナントの一致はアプリ本体の不変条件とし、外部のPDPへ委譲しない。ロールとグループの意味の評価だけを、AccessControlAdapterへ委譲する。
  • テナントに従属するデータは、DBの複合制約とDB側のテナントガードで分離する。キャッシュ、ジョブ、監査など現存する利用側も、テナントとセッションの世代で分離する。MCPは、テナントに束縛された認証情報がない間は saas-multitenant を起動前に拒否し、クライアントが入力したtenantIdでは代替しない。
  • ワークスペースのデータ面、テナント管理、プラットフォームの制御面は、ルート、認証のオーディエンス、ケイパビリティを分離する。プラットフォームの運用権限から、文書の読み取りを暗黙に導き出さない。
  • テナントが不明または不一致のとき、メンバーシップが停止しているとき、PDPやアダプタに障害があるとき、DBのガードが成立しないときは、読み取りを含めて安全側で拒否する。
  • 型と永続の制約は schemas.md、エンドポイントとステータス、エラーはapi.md、プロファイルのゲートはruntime_parameter_registry.md、実装と検証の履歴は 01_Plans/issues/done/issue-SAAS-TENANT-01-tenant-context-and-storage-foundation.md を正本とする。
