strictモードの例外緩和と承認フローの仕様

SUI_ALLOW_JIT_PROVISIONING=false（strict）を本番標準としつつ、例外的に true へ緩和する際の承認フローを設計レベルで固定する。人間が短時間で判断でき、AIエージェントが推測で承認フローを補完しないことを目的とする。

状態：承認済み（2026-03-06、D1〜D4を固定） 適用範囲は組織運用の一時的な緩和のみ

本書が正本である（新規設計文書はHTML単独とする。AGENTS.md §3）。適用範囲は、組織運用で SUI_ALLOW_JIT_PROVISIONING=false を一時的に緩和する場合に限る。個人OSSの日常の開発や通常の復旧に使う承認フローではない。2者承認を用意できない場合は例外を有効化せず、strict設定を維持する。

01

目的・非目標・固定済み契約

目的　strictを本番標準としつつ、例外的に緩和する際の承認フローを設計レベルで固定する。(1)人間が「何を決めれば作業開始できるか」を短時間で判断できること、(2) AIエージェントが推測で承認フローを補完せず停止条件を守れること。

非目標　承認のバイパスをコードで実装すること、監査スキーマにPIIを追加すること、既存のSafeModeとread-onlyの優先順位を変更することは、いずれも目的としない。

固定済み契約内容
strict標準SUI_ALLOW_JIT_PROVISIONING=false。例外緩和は通常「一時変更」として扱う
恒常運用の扱い組織ポリシーで true を恒常的に採用する場合は、「例外フロー」ではなく、別途「公開運用プロファイル」を定義し、審査し、監査する
2者承認責務Security Officer + System Owner
実行責務Platform Operator（承認済み変更のみ実行）
監査最小項目時刻、理由、承認者、対象環境、復旧条件
PII非保存サブジェクトの生値、rolesとgroupsとpolicyRefの生値、自由記述のPIIを保存しない

03

役割分離（RACI）

タスクSecurity OfficerSystem OwnerPlatform Operator
申請妥当性レビュー（安全）A/RCI
申請妥当性レビュー（業務継続）CA/RI
例外発動実行IIA/R
復旧実行（strict復帰）CCA/R
監査記録の整合確認AAR

凡例はA（Accountable、説明責任）、R（Responsible、実行責任）、C（Consulted、相談先）、I（Informed、報告先）である。承認（A/R）と実行（A/R）を分離し、単独の判断で緩和が常態化しないようにする。

HIL-RSガバナンス連携の補強（A1の契約強化）　Security Officer / System Ownerは承認責務のみ、Platform Operatorは実行責務のみを負う。requester と approver の兼務は禁止し、approver_a != approver_b を必須とする（二者統制）。Approval Record=Pending が1件でも残る場合、Approved / ActiveException への遷移は禁止する。decisionQueueTransition は Pending → Approved または Pending → Rejected のみ許可し、Pendingの迂回を禁止する。

非矛盾ルール（§8.4）　停止条件は「例外を有効化してよいか」の判定にのみ使用する。復旧条件は「すでに有効な例外をstrictに戻す」判定にのみ使用する。両方が同時に成立した場合は、復旧実行を停止記録より優先する（先にstrict復帰を完了させる）。

復旧完了判定　SUI_ALLOW_JIT_PROVISIONING=false へ復帰済みで、endedAtと復旧理由が記録済みで、事後レビューの期限と担当も記録済みであること。

08

CDC（Change Decision Contract）と用語

AUTH系の設計変更は、実装や運用へ反映する前に CDC を必ず確定する。C（Context）は変更対象、非目標、D1〜D4との整合を指す。D（Decision）は採択または却下した選択肢、理由、適用開始日、失効条件を指す。C（Consequence）は影響範囲、検証方法、ロールバック条件、停止条件を指す。CDCが未確定の変更要求は DraftRequest のままとし、ApprovalPending へ遷移させない。

strictSUI_ALLOW_JIT_PROVISIONING=false の状態。未登録主体を拒否する
例外緩和...=true に変更して運用すること
承認フロー例外緩和を実施してよいかを決める手順
復旧例外終了後に ...=false へ戻すこと
Q1〜Q10現在未確定の運用判断項目（順序、TTL、代理承認など）

運用プロファイルの選択　(1) strict標準プロファイル（推奨の既定）では、falseを通常運用とし、trueは承認付きの一時運用とする。(2)公開運用プロファイル（条件付き）では、trueを継続して運用する（SNSのような多数の利用者による閲覧など、事前登録制を維持しにくい場合）。この場合は、アクセス境界、監視、フェイルセーフ、定期レビューによる補完統制を 04_Documentation/security_operational_guidelines.md に示す。どちらのプロファイルでも、SafeModeの既定ON、PIIの最小化、監査最小化の契約は維持する。

総括

本仕様の骨格は単純である。承認と実行を分離し（RACI）、停止条件を「有効化前」に、復旧条件を「有効化後」に限定し、両者が競合したら復旧を優先する。D1〜D4の固定値は、この骨格に具体的な数値（TTLは4時間、最大継続は2時間、代理承認なし、48時間でのレビュー）を与え、AIエージェントを含む実行者が推測で承認フローを補完する余地をなくす。
