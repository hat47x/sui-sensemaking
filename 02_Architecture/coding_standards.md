# コーディング規約（シンプルさと安全性）


> 環境変数・実行パラメータの正本は `02_Architecture/runtime_parameter_registry.md` である。本書には必要最小限だけを書き、追加や改名のときは正本を先に更新する。
この文書は、`sui-sensemaking` のコードをシンプルかつ安全に保つための、実務向けのルールとレビュー観点を定義します。

- 対象: `03_Implement/frontend` / `03_Implement/backend`
- 優先順位: `00_Prompt` / `01_Plans` / `02_Architecture` に従う
- バッドスメル是正の意思決定: `01_Plans/adr/ADR-0018-coding-standards-and-smell-remediation.md`

## 1. 規約（必須）

### 1.1 シンプルさ（複雑性の制御）

1. 責務分割
   - 1ファイル1責務を原則とする。
   - UIコンポーネントは「表示」「状態管理」「ドメイン処理」を分離する。
2. ファイル肥大化の抑制
   - 新規追加時は300行を超える前に分割を検討する。
   - 既存の巨大ファイルに機能を追加するときは、同時に最低1単位の抽出（hook / util / component）を行う。
3. 重複排除
   - 同じロジックが2回以上出る場合は関数にする。
   - UIの色・余白・フォントは定数にして再利用する。
4. 命名
   - 識別子は英語で、意図が読める名前にする（略語はドメインで既知のものだけ）。

5. 長期保守性を最優先する
   - 本プロジェクトは長期運用を前提とする。短期的な場当たり修正より、変更しやすさと回帰への強さを優先する。
   - 設計判断では疎結合・高凝集を優先し、依存の向きを明確に保つ。
6. 設計原則の実践
   - SOLID / DRY / KISS / YAGNI / 単一抽象度（SLAP）を、実装判断の基準として使う。
   - 汎用化の根拠がない抽象化は追加しない（将来の予測だけで拡張点を作らない）。
7. 自己説明的なコードを優先
   - 命名と構造で意図が読める実装を優先する。コメントには「何をしているか」ではなく「なぜそうしたか」を補う。

### 1.2 セキュリティ（安全な実装）

1. 入力検証を先に行う
   - APIは「存在確認」「型・範囲」「参照整合」をハンドラの先頭で検証する。
   - フロントエンドのimport/exportでも、スキーマ検証を省略しない。
2. 例外は狭く捕捉する
   - `except Exception` は原則禁止。
   - 期待する例外型（例: `ValidationError`, `JSONDecodeError`）を明示して捕捉し、ログとメッセージを分ける。
3. 安全な既定値を維持する
   - SafeModeの既定ONを変更しない。
   - share/export系は「漏えいしない初期値」を守る。
4. 危険なAPIの禁止
   - `eval` / `new Function` / `dangerouslySetInnerHTML` は禁止（設計レビューで例外が承認された場合のみ許す）。
5. 機密情報の直書き禁止
   - APIキーやトークンは、コード・fixture・ログに保存しない。
   - 設定は環境変数から注入する。
6. 型安全性を維持する
   - TypeScriptでは `any` と安易な型アサーション（`as any` / `!`）を原則禁止する。
   - 例外的に型を緩める必要があるときは、範囲を局所化し、理由をコメントまたはPRに明記する。

### 1.3 ドキュメンテーションとコメント

1. ドキュメンテーションの最小要件
   - 公開API、複雑な分岐、セキュリティ境界には、実装の理由（Why）を簡潔に残す。
   - コメントは最新に保ち、実装と矛盾する説明を残さない。

### 1.4 テスト・検証

1. 変更に対応するテストを同時に追加する
   - バグ修正では、再現テストを先に書く（または同時に追加する）。
2. 最低限の実行コマンド
   - Frontend: `npm run typecheck && npm run test`
   - Backend: `ruff check src tests && pytest`
3. セキュリティ境界に触れる変更
   - import/export/safeMode/LLM連携は、正常系と異常系の両方をテストする。
4. アプリ改修時のE2E確認
   - `03_Implement/*` を変更した場合は、原則として `docker compose` で `web+api+db` を連動させて確認する。
   - Dockerが未導入の環境では、SQLite代替のE2E（`backend:8000` + `frontend:4173`）で連動を確認する。
   - UIを変更したときは、原則としてPlaywright E2Eテストを追加・更新する（最低限: `npx playwright test e2e/i18n_locale_query_equivalence.spec.ts --reporter=line`）。
   - E2E手順の正本は `03_Implement/frontend/docs/e2e_testing.md` とし、利用者向けの確認手順は `04_Documentation/acceptance_check.md` に分ける。E2E手順を変更したら、同じPRで `installation.md` / `operations.md` / `CONTRIBUTING.md` の記述と食い違わないか確認する。
   - 正本のどちらが正しいか判断しにくい不足や不整合は、あるべき状態を整理したIssueを起票してから同期する（ADRに作業トラッキングを混ぜない）。
   - それでも実行できない環境に限り、未実施の理由、代替検証、後続の確認手順、Composeを確認していないことによるリスクの差分をPRに書く。

### 1.5 Frontendの品質ゲート

CIのfrontendゲートは `frontend-typecheck`（`tsc --noEmit`）と `frontend-test`（`vitest run` 全件）の2つであり、どちらも常にエラーで失敗させる。

独立したリンタは導入していない。`npm run lint` は `npm run typecheck` の別名である。将来リンタを入れる時点で、専用ジョブと運用方針を足す。

## 2. レビュー時のチェックリスト（PRに貼り付け推奨）

- [ ] 変更は上位文書（`00_`〜`02_`）と矛盾しない
- [ ] 1ファイル1責務を守れている（巨大化していない）
- [ ] 重複したロジックやスタイルを追加していない
- [ ] 入力検証とエラーハンドリングが明示されている
- [ ] `except Exception` / `any` / 危険なAPIを増やしていない
- [ ] 影響範囲に対するテストを追加・更新した
- [ ] E2Eの証跡（Playwrightの追加・更新、または未実施の理由と代替検証）をPR本文に書いた
- [ ] E2E関連ドキュメント（acceptance_check/installation/operations/CONTRIBUTING）を、正本（03_Implement/frontend/docs/e2e_testing.md）と同期した
- [ ] E2Eの不整合でどちらが正しいか判断しにくい場合、Issueを起票した

---

## 3. 再発防止の運用ルール

1. 規約からの逸脱は「技術的負債」として明示する
   - すぐに直せない場合は、Issueに「理由・解消期限・担当」を記録する。
2. 巨大ファイルは段階的に分解する
   - 機能追加のPRで、最低1つは責務を外へ抽出する。
3. 静的検査の強化を続ける
   - Frontendのlint（ESLint導入など）をロードマップで管理し、CIで段階的に必須にする。
