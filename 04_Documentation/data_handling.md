# データ取り扱い

対象読者: sui-sensemakingでドキュメント、export、share、AI提案、監査ログ、障害調査ログを扱う管理者、運用担当者、レビュー担当者。

目的: データがどこに保存され、どの場面で外部サービスと共有される可能性があり、共有前に何を確認するかを説明します。

読後にできること: 入力、保存、AI提案、export、share、障害調査の前に、残してよい情報と削るべき情報を判断できます。

## 最初に押さえること

- ドキュメント本文、カード、島、レビュー状態はsui-sensemakingの通常データとして保存されます。
- ブラウザには保存領域（local storage）、キャッシュ、ダウンロードしたファイルなど、利用者端末側に残る情報があります。
- LLM、監査ログのHTTP連携（audit HTTP）、外部アクセス制御を有効にすると、設定したサービスに情報を連携する可能性があります。
- exportやshareは、アプリ内の情報を取り出して共有できる操作です。実行前に出力範囲を確認します。
- ログやスクリーンショットを共有するときは、秘密情報、API key、内部承認履歴、生の顧客情報を含めません。

## データの種類

| 区分 | 例 | 扱い方 |
| --- | --- | --- |
| 通常保存 | ドキュメント本文、カード、島、レイアウト、レビュー状態 | アプリの主要データとして保存できます。 |
| 最小保持 | 表示名、メールアドレス、外部 identity 参照 | 必要な場面だけに限定し、export 前に残す必要があるか確認します。 |
| 一時利用 | roles, groups, policyRef, trace id, provider 応答時間 | 調査や判定のために使い、長期保存や共有を前提にしません。 |
| 保存・共有禁止 | password, token, secret, raw assertion, API key, 生の秘密情報 | 入力、ログ、export、問い合わせメモ、スクリーンショットに含めません。 |

判断に迷う情報は、まず「最小保持」または「保存・共有禁止」として扱います。必要性を説明できてから範囲を広げます。

## 主な流れ

| 場面 | 残る場所 | 共有・連携の可能性 | 確認すること |
| --- | --- | --- | --- |
| ドキュメント作成・保存 | backend DB、ブラウザ cache | 通常はアプリ内だけ | 秘密情報を本文やカードに入れていないか。 |
| AI 提案 | backend、LLM provider | `SUI_LLM_PROVIDER` が `local` や `large-scale` の場合 | 利用する provider、明示的な利用許可（opt-in）、許可先（allowlist）、共有する情報。 |
| export | ダウンロードしたファイル、共有先 | 利用者が共有した先 | 内部メモ、秘密情報、不要な identity 情報がないか。 |
| share | 共有 URL、共有先の閲覧者 | 共有先の範囲 | visibility、SafeMode、readOnly、共有相手。 |
| audit HTTP | 監査ログ連携の接続先 | `SUI_AUDIT_EXPORT_ENABLED=true` の場合 | 接続先（endpoint）、API key、SafeMode 中の許可理由。 |
| access control | 外部 PDP | `SUI_ACCESS_CONTROL_ADAPTER=external_http` の場合 | PDP の接続先（endpoint）、失敗時の扱い（fail-safe）、連携する属性の最小化。 |
| 障害調査 | ログ、スクリーンショット、調査メモ | 問い合わせ先やチーム内共有 | 再現手順と status を残し、秘密情報は削る。 |

## 外部サービスと共有する前の判断

外部サービスと共有する設定を有効にする前に、次を確認します。

- 共有先を説明できる。
- どの情報を共有するか説明できる。
- どの情報を共有しないか説明できる。
- 失敗時の動作が安全側に倒れる。
- SafeMode中に例外を許可する場合、理由を運用記録に残せる。

説明できない項目がある場合は、設定を有効にせず、`SUI_LLM_PROVIDER=none` やaudit HTTP連携を無効にしたまま確認します。

## Export と share 前チェック

- [ ] 出力対象のドキュメントに秘密情報や内部承認履歴がない。
- [ ] レビュー状態と未レビュー情報の扱いを確認した。
- [ ] identity情報を残す必要があるか確認した。
- [ ] visibilityが共有範囲の意図と合っている。
- [ ] SafeModeやreadOnlyの警告を無視していない。
- [ ] 共有先が必要最小限になっている。
- [ ] カードの通し番号・原データ参照（出典）を含める必要が本当にあるか確認した（既定では含めない）。
- [ ] ダウンロードしたファイルの保管先と削除方針を説明できる。

「共有と再現」パネルでは、目的を選んだあとに `共有前チェック` を確認します。この欄にはSafeMode、viewの公開範囲、パックの公開範囲、未レビュー情報の扱い、出力形式、レビューパックの粒度、出典参照（通し番号・原データ）の扱いがまとまって表示されます。共有前は、画像のようにSafeModeが有効であること、公開範囲が意図した範囲であること、未レビュー情報や出典参照を含めない設定になっていることを確認してからexportします。レビューパックの書き出しでは、未レビュー・違和感・矛盾のいずれかが残っている場合、書き出しの直前にもう一度件数を示す確認画面が表示されます。

## 障害調査で残す情報

障害調査では、原因を追える最小限の情報だけを残します。

残してよい情報は次のとおりです。

- 発生日時
- 対象URL
- 操作手順
- 期待した結果
- 実際の結果
- API status code
- 対象ドキュメントID
- 秘密情報を除いたログの抜粋

残さない情報は次のとおりです。

- API key、token、password
- 生の認証assertion
- 顧客や利用者の未加工データ
- 組織内の承認履歴
- 調査に不要なスクリーンショット全体

詳しい調査手順は [diagnostics.md](diagnostics.md) を参照してください。

### サポート診断バンドル

画面から生成できる診断バンドル（`diag-bundle.v1`）は、上記「残してよい情報」よりさらに狭い固定の許可リストだけを含みます。対象ドキュメントの本文・ID、entity id/ref、API key/token/password、内部URL、個人情報、生のUserAgent、error message/stackはSafeModeの状態に関わらず常に除外されます。含まれる項目と除外項目は [diagnostics.md](diagnostics.md) を参照してください。生成は明示操作のみで、自動送信は行いません。

## 復旧時のデータ確認

復旧時は、データを急いで書き換える前に、何が壊れているか、どこまで安全に再試行できるかを確認します。この文書では、利用者や運用担当者が最初に確認する観点だけを扱います。

実DB復旧コマンド、管理UI/API実装、削除、所有者移管などは、環境ごとに影響が大きいため、この公開手順だけで実行しないでください。

### 最小チェック順序

1. ドキュメントのversionが現在のアプリで扱える範囲か確認する。
2. ドキュメント本文、カード、レビュー状態、判断ログが同じ対象を指しているか確認する。
3. 標準画面で扱うデータと、埋め込みや連携で扱うデータを分けて影響範囲を記録する。
4. 共有前確認としてSafeModeが有効であること、未レビュー本文や個人情報が出力に混ざらないことを再確認する。

### 復旧演習で残す最小証跡

復旧演習は、各組織のバックアップ方針を決めるための材料です。保持期間、暗号化、保管先、承認手順をこの文書だけで固定せず、次の事実を残します。

- どのDB種別を、どのアプリrevisionで確認したか。
- 代表Documentが復元後も同じ `id` と `version` で読み込めたか。
- 判断ログが対象Documentに紐づき、時系列やsnapshot単位の順序が保たれたか。
- SafeModeと共有前確認が復旧後も有効で、未レビュー本文や個人情報を不用意に共有しない状態だったか。
- PostgreSQLなど本番相当の復旧確認を実行できなかった場合、その理由と再開条件。

### 停止条件

- 上記4項目のうち1つでも未確認のまま復旧完了扱いにしない。
- 確認や調整を繰り返しても原因が絞れない場合は、利用を継続せず、影響範囲と未解決点を記録して詳しい調査へ引き継ぐ。
