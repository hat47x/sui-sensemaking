# データの取り扱い

想定読者: sui-sensemakingで、文書、書き出し、共有、AIによる提案、監査記録、障害調査のログを扱う管理者・運用担当者・確認担当者。

この文書では、データの保存先、外部サービスと共有される場面、共有前に確認すべき事項を説明します。

入力、保存、AIによる提案、書き出し、共有、障害調査の各場面で、残してよい情報と削るべき情報を判断できるようにするための案内です。

## 最初に押さえること

- 文書の本文、カード、島、レビューの状態は、sui-sensemakingの通常のデータとして保存されます。
- ブラウザを使う端末にも、ローカルストレージ、キャッシュ、ダウンロードしたファイルなどの情報が残ります。
- 言語モデル（LLM）、監査ログのHTTP連携、外部のアクセス制御を有効にした場合は、設定したサービスへ情報が送られることがあります。
- 書き出しと共有は、アプリケーション内の情報を取り出し、ほかの人に渡せるようにする操作です。実行する前に、出力の範囲を確認します。
- ログやスクリーンショットを共有するときは、秘密情報、APIキー、内部の承認履歴、顧客の生の情報を含めません。

## データの種類

| 区分 | 例 | 扱い方 |
| --- | --- | --- |
| 通常保存 | 文書の本文、カード、島、配置、レビューの状態 | アプリの主要なデータとして保存できます。 |
| 最小限だけ保持 | 表示名、メールアドレス、外部のID参照 | 必要な場面に限り、書き出す前に残す必要があるかを確認します。 |
| 一時利用 | 役割（roles）、グループ（groups）、`policyRef`、追跡用の識別子（trace id）、提供元の応答時間 | 調査や判定のために使い、長期の保存や共有を前提にしません。 |
| 保存と共有を禁止 | パスワード、トークン、シークレット、認証アサーションの生の値、APIキー、秘密情報の生の値 | 入力、ログ、書き出し、問い合わせのメモ、スクリーンショットに含めません。 |

扱いを判断できない情報は、まず「最小限だけ保持」または「保存と共有を禁止」の対象として扱います。必要性を説明できてから、範囲を広げます。

## 主な流れ

| 場面 | 残る場所 | 共有や連携の可能性 | 確認すること |
| --- | --- | --- | --- |
| 文書の作成と保存 | サーバー側のデータベース、ブラウザのキャッシュ | 通常は、アプリの中だけ | 秘密情報を、本文やカードに入れていないか。 |
| AIの提案 | サーバー側、言語モデルの提供元 | `SUI_LLM_PROVIDER` が `local` や `large-scale` のとき | 使うプロバイダ、明示的な利用の許可（opt-in）、接続を許可する宛先（許可リスト）、共有する情報。 |
| 書き出し | ダウンロードしたファイル、共有先 | 利用者が共有した先 | 内部のメモ、秘密情報、不要なID情報が含まれていないか。 |
| 共有 | 共有URL、共有先の閲覧者 | 共有先の範囲 | 公開範囲、SafeMode、読み取り専用の設定、共有する相手。 |
| 監査ログのHTTP連携 | 監査ログの連携先 | `SUI_AUDIT_EXPORT_ENABLED=true` のとき | 接続先（エンドポイント）、APIキー、SafeMode中に許可した理由。 |
| アクセス制御 | 外部の認可判断サービス（PDP） | `SUI_ACCESS_CONTROL_ADAPTER=external_http` のとき | PDPの接続先（エンドポイント）、失敗したときの扱い（フェイルセーフ）、連携する属性を最小限にしているか。 |
| 障害調査 | ログ、スクリーンショット、調査のメモ | 問い合わせ先や、チーム内での共有 | 再現の手順とステータスを残し、秘密情報は削る。 |

## 外部サービスと共有する前の判断

外部サービスと共有する設定を有効にする前に、次を確認します。

- 共有する先を説明できる。
- どの情報を共有するかを説明できる。
- どの情報を共有しないかを説明できる。
- 失敗した場合の動作が、安全側になる。
- SafeMode中に例外を許可するときは、その理由を運用の記録に残せる。

説明できない項目がある場合は、設定を有効にせず、`SUI_LLM_PROVIDER=none`のまま、監査ログのHTTP連携も無効にして確認します。

## 書き出しと共有の前のチェック

- [ ] 出力する文書に、秘密情報や内部の承認履歴がない。
- [ ] レビューの状態と、未レビューの情報の扱いを確認した。
- [ ] ID情報を残す必要があるかを確認した。
- [ ] 公開範囲が、共有する範囲の意図と合っている。
- [ ] SafeModeや読み取り専用の警告を、無視していない。
- [ ] 共有する先が、必要最小限になっている。
- [ ] カードの通し番号と、原データへの参照（出典）を含める必要が本当にあるかを確認した（既定では含めない）。
- [ ] ダウンロードしたファイルの保管先と、削除の方針を説明できる。

「共有と再現」パネルでは、目的を選んだ後、`共有前チェック`を確認します。この欄には、SafeMode、ビューの公開範囲、パックの公開範囲、未レビューの情報の扱い、出力形式、レビューパックの粒度、出典への参照（通し番号と原データ）の扱いが、まとめて表示されます。共有する前に、画像のようにSafeModeが有効であること、公開範囲が意図した範囲であること、未レビューの情報と出典への参照を含めない設定になっていることを確認してから、書き出します。レビューパックを書き出すときは、未レビュー、違和感、矛盾のいずれかが残っていると、書き出しの直前に、もう一度、件数を示す確認画面が表示されます。

## 障害調査で残す情報

障害を調べるときは、原因を追える最小限の情報だけを残します。

残してよい情報は、次のとおりです。

- 発生日時
- 対象のURL
- 操作の手順
- 期待した結果
- 実際の結果
- APIのステータスコード
- 対象の文書ID
- 秘密情報を除いたログの抜粋

残さない情報は、次のとおりです。

- APIキー、トークン、パスワード
- 認証アサーションの生の値
- 顧客や利用者の、加工していないデータ
- 組織内の承認履歴
- 調査に不要な、画面全体のスクリーンショット

詳しい調査の手順は、[diagnostics.md](diagnostics.md) を参照してください。

### サポート診断バンドル

画面から作れる診断バンドル（`diag-bundle.v1`）に含まれるのは、固定の許可リストにある項目だけです。上の「残してよい情報」よりも、さらに範囲が狭くなっています。対象の文書の本文とID、エンティティのIDと参照、APIキー、トークン、パスワード、内部のURL、個人情報、UserAgentの生の値、エラーメッセージとスタックトレースは、SafeModeの状態にかかわらず、常に除外されます。含まれる項目と除外される項目は、[diagnostics.md](diagnostics.md) を参照してください。生成は明示的に操作したときだけで、自動では送信しません。

## 復旧のときのデータの確認

復旧のときは、データを急いで書き換える前に、何が壊れているか、どこまで安全に再試行できるかを確認します。この文書では、利用者や運用担当者が最初に確認する観点だけを扱います。

実際のDBを復旧するコマンド、管理用のUIやAPIの実装、削除、所有者の移管などは、環境ごとの影響が大きいため、この公開の手順だけで実行しないでください。

### 最小の確認の順序

1. 文書のバージョンが、現在のアプリで扱える範囲か確認する。
2. 文書の本文、カード、レビューの状態、判断ログが、同じ対象を指しているか確認する。
3. 標準の画面で扱うデータと、埋め込みや連携で扱うデータを分けて、影響の範囲を記録する。
4. 共有前の確認として、SafeModeが有効であることと、未レビューの本文や個人情報が出力に混ざらないことを、もう一度確認する。

### 復旧の演習で残す最小の記録

復旧の演習は、各組織のバックアップの方針を決めるための材料です。保持期間、暗号化、保管先、承認の手順は、この文書だけで固定せず、次の事実を残します。

- どのDBの種類を、どのアプリのリビジョンで確認したか。
- 代表的な文書が、復元したあとも、同じ `id` と `version` で読み込めたか。
- 判断ログが対象の文書に結び付いていて、時系列やスナップショットごとの順序が保たれたか。
- SafeModeと共有前の確認が、復旧のあとも有効で、未レビューの本文や個人情報を、不用意に共有しない状態だったか。
- PostgreSQLなど、本番に近い環境での復旧確認を実行できなかったときは、その理由と、再開できる条件。

### 中止する条件

- 上の4項目のうち、1つでも未確認のまま、復旧が完了したものとして扱わない。
- 確認や調整を繰り返しても原因を絞れないときは、利用を続けず、影響の範囲と未解決の点を記録して、詳しい調査に引き継ぐ。
