# リリース手順

対象読者: sui-sensemakingのリリース、検証版の共有、公開前の確認を担当する人。

目的: 利用者が触れる状態へ変更を出す前に、品質、安全性、文書、受け入れ確認を人間が確かめ、タグと検証の記録を対応付けるための、最小の手順をまとめます。

## 現在の前提: GitHub Actionsによる自動リリースは無効

現在、このリポジトリには、常設のGitHub Actionsのリリース用ワークフローを置いていません。タグをpushしても、自動のビルド、GitHub Actionsのアーティファクト、GitHub Release、コンテナやパッケージのレジストリへの公開は行われず、自動で生成される成果物はありません。

そのため、この文書の現在の手順が扱うのは、次の範囲です。対象のコミットを手動で検証する。必要ならローカルでビルドする。確認が済んだコミットにタグを付ける。結果を記録する。継続的に公開して配布することを始めるときは、公開する場所、アーティファクトの構成、保持期間、チェックサム、来歴（provenance）、SBOM、署名、backendイメージのレジストリ、撤回の方法を、別のIssueかADRで決めます。そのうえで、自動化とこの文書を、同じ変更で更新します。

## リリース前のチェック

```bash
git status -sb
git diff --check
```

この文書でいうリリースは、正式版だけでなく、検証版や限定した共有も含めて、利用者が触れる状態へ変更を出すことです。

## 前提知識

リリース担当者は、実装の詳細をすべて理解している必要はありません。ただし、次の違いは確認できるようにしておきます。

| 用語 | 意味 |
| --- | --- |
| ビルド | 利用者が実行できる形に、frontendなどを組み立てること |
| テスト | 期待した動作を、機械的に確認すること |
| スモークテスト | 主要な操作だけを、短時間で手動で確認すること |
| ロールバック | 問題が出たときに、前の状態へ戻すこと |

## リリース判断の流れ

常設CIは現在無効なので、次の確認は、タグを打つ前に、タグの対象にする予定のコミットSHAに対して自分で実行し、結果をリリースの記録に残します。

1. 差分の範囲を確認する。
2. 影響があるテストを実行する。
3. 手動のスモークテストで、利用者の主要な操作を確認する。
4. セキュリティ、SafeMode、外部サービスとの共有に関する安全上の境界が、後退していないことを確認する。
5. データの取り扱いの観点で、書き出し、共有、ログ、外部サービスとの共有の扱いを確認する。
6. ロールバックの方針を確認する。

frontendでは、次を実行します。

```bash
cd 03_Implement/frontend
npm ci
npm run typecheck
npm run test
npm run build
```

backendでは、次を実行します。

```bash
cd 03_Implement/backend
python -m pytest
```

Docker Composeでは、次を実行します。

```bash
cd 03_Implement/deploy
docker compose up --build -d
curl -fsS http://localhost:8080/api/healthz
```

## タグの作成手順

1. 上の「リリース判断の流れ」を、対象のコミットSHAに対して実行し、必要な確認が成功することを確かめる。説明できない失敗があるときは、タグを作らない。
2. `CHANGELOG.md` の `[Unreleased]` を、タグと同じバージョン番号と当日の日付の見出しに切り出す。
3. タグ名はSemVerの形式 `vX.Y.Z` とし、対象は、手順1で確認したコミットSHAに限る。
4. 一度作成したタグは、強制的に更新（force pushやタグの付け直し）しない。誤りがあったときは、新しいバージョン番号でやり直し、誤ったタグは撤回したものとして記録する。
5. タグをpushする。現在は、GitHub Actionsによる後続の処理がないため、pushが成功しただけでは、ビルドや配布が完了したとは扱わない。
6. 下の「リリースの記録に残す項目」を記録する。

## 成果物の扱い

現在は、タグのpushをきっかけに、自動で生成され、自動で保存される成果物はありません。frontendのビルド結果やDockerイメージを検証に使ったときも、その結果は、検証を行った環境にだけ存在します。

第三者へ継続して配布するアーティファクトを定義するときは、少なくとも次を決めてから、自動化します。

- 何を正式な配布物とするか。
- どこから取得できるか。
- 対象のタグとコミットSHAを、どう対応付けるか。
- 保持する期間と、撤回の方法。
- チェックサム、来歴、SBOM、署名を、どう扱うか。
- backendのイメージを、レジストリへ送るか。

## CHANGELOGとの対応

`CHANGELOG.md` は、[Keep a Changelog](https://keepachangelog.com/ja/1.1.0/) の形式で書き、SemVerに従います。`[Unreleased]` から版を切る条件は、次のとおりです。

- タグを作成する直前に、`[Unreleased]` の内容を `## [X.Y.Z] - YYYY-MM-DD`（タグと同じバージョン番号と、当日の日付）に書き換える。
- 新しい空の `[Unreleased]` を、見出しだけ残す。
- `[Unreleased]` のまま、タグをpushしない。版とタグは、1対1で対応させる。

## リリースの記録に残す項目

- タグ（`vX.Y.Z`）
- 対象のコミットSHA
- 実行したテスト、文書のチェック、ビルドと、その結果
- ゲートの判断（`PRODUCT-QA-01` の、可否の判断）
- 手動のスモークテストの結果
- 共有した成果物があるときは、その生成の方法と取得できる場所
- 既知の制限
- ロールバックと撤回の方針

GitHub Actionsのワークフローを将来また導入したときは、ワークフローの実行、アーティファクトの名前、取得できる場所、保持の範囲も、記録の対象に戻します。

## 手動での確認

- [ ] アプリが開く。
- [ ] 新しい文書を作成できる。
- [ ] カードを追加して、移動できる。
- [ ] 保存して再読み込みしても、内容が残る。
- [ ] 共有や書き出しに、秘密情報や内部の作業ログが含まれていない。
- [ ] SafeModeの既定の動作が、緩んでいない。
- [ ] LLMのプロバイダが、意図した値になっている。
- [ ] 監査ログのHTTP連携や外部のアクセス制御を有効にしたときは、連携先と、失敗したときの動作を説明できる。

## 失敗したときの扱い

次のいずれかに当てはまるときは、リリースを止めます。

- ビルド、テスト、型の検査、文書のチェックの失敗の理由を、説明できない。
- SafeMode、共有と書き出し、LLMのプロバイダに関する安全上の境界が、後退している。
- 秘密情報、内部のURL、顧客の生の情報が、文書や書き出しに混ざっている。
- 受け入れ確認の主要な操作を、再現できない。

止めること自体は、異常ではありません。利用者に影響する不確実な点を見つけた状態なので、原因、回避策、再開できる条件を記録してから、次の確認に進みます。誤って作成したタグは強制的に更新せず、撤回したものとして記録し、新しいバージョン番号でやり直します。
