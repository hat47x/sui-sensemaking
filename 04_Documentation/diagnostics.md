# 診断と障害調査

対象読者: 画面表示、保存、AI提案、ワーカー処理の問題を調べる開発者、QA、運用担当者。

目的: 障害が起きたときに最初に見る場所、切り分けの順序、記録しておく情報をまとめます。

読後にできること: 画面、API、DB、外部接続のどこで問題が起きているかを切り分け、共有に必要な情報を安全に記録できます。

## 最初に確認すること

1. どのURLで起きたか。
2. どの操作で起きたか。
3. 直前に、保存、インポート、書き出し、AI提案、レビュー操作を行ったか。
4. APIは応答しているか。
5. ブラウザのコンソールとネットワークに、エラーが出ているか。

## 調査の考え方

障害を調べるときは、まず、画面だけの問題か、APIも失敗しているか、DBまで影響しているかを分けます。原因を一度に決めつけず、利用者に見えている症状から、奥へ進みます。

最初の5分は、原因の断定より、再現条件の確認を優先してください。発生したURL、操作の手順、APIのステータス、コンソールのエラーがそろうだけで、そのあとの調査がかなり楽になります。

| 層 | 見るもの |
| --- | --- |
| 画面 | ブラウザのコンソール、表示の崩れ、操作できない箇所 |
| API | HTTPステータス、`/healthz`（死活確認）と `/readyz`（DBへの到達性とスキーマの世代）、backendのログ |
| DB | `db` の状態、マイグレーション、保存した結果 |
| 外部接続 | LLMのプロバイダ、監査ログの連携先、アクセス制御の接続先（エンドポイント） |

## 前提知識

この文書での調査では、次の3つを区別できれば十分です。

| 用語 | 意味 |
| --- | --- |
| frontend | ブラウザで動く、画面の側です。 |
| backend / API | 保存、AI提案、認証などを処理する、サーバーの側です。 |
| DB | 文書や操作の結果を保存するデータベースです。 |

## ヘルスチェック

Docker Composeの場合は、次のとおりです。

```bash
curl -fsS http://localhost:8080/api/healthz   # 死活確認のみ（何も検査しません）
curl -s http://localhost:8080/api/readyz      # DBへの到達性とスキーマの世代
docker compose ps
docker compose logs api --tail=200
```

直接起動した場合は、次のとおりです。

```bash
curl -fsS http://127.0.0.1:8000/healthz
```

> **ヘルスチェックの意味**: `/healthz` は、プロセスが生きているかだけを確認し、DBには触れません。DBへの到達性と、マイグレーションの適用状態（スキーマが最新と一致しているか）まで確認するには、`/readyz` を使います。DBが止まっているときと、スキーマが一致しないときは、503を返します。ビルドのリビジョンは `/version` で確認できます。

## ブラウザで見る場所

- Console: JavaScriptのエラー、ワーカーのエラー、失敗した取得。
- Network: `/api/docs/<doc_id>`、`/api/ai/*`、ステータスコード。
- Application / Storage: ローカルストレージやキャッシュに、古い状態が残っていないか。

画面内の診断は、右側のパネルにあるレイアウトとアウトラインの付近から実行できます。実行すると、品質レポート、所見の件数、メトリクスが表示されます。障害調査のメモには、この結果とAPIのステータスを、合わせて残します。

## よくある切り分け

| 症状 | 主な確認 |
| --- | --- |
| 画面が真っ白になる | frontendのビルド、コンソールのエラー、nginxのログ |
| `Internal Server Error` が表示される | backendが起動しているか、`/api/healthz` が成功するか。標準サンプルの `doc_phase1_canvas` は、初めてブラウザで表示したときに作られます。そのため、初回の表示の前に `/api/docs/doc_phase1_canvas` を呼ぶと404になりますが、これは正常です。5xxが返るときだけ、backendを調べます。 |
| 保存に失敗する | APIのステータス、`X-API-Key`、backendのログ、DBへの接続 |
| `Database driver for backend '...' is not available` でbackendやマイグレーションが止まる | [installation.mdの、DBごとのpip extraの表](installation.md#sqlite以外の検証済みdbを直接使う場合)を確認し、同じ仮想環境に、対象のextraを導入します。URLやパスワードを、診断ログに貼らないでください。 |
| `password authentication failed for user "sui_sensemaking"` がbackendのログに出る | まず、`env \| grep -i sui_sensemaking`（exportした変数がcomposeの既定値を上書きし、`down -v` でも直りません）と、`docker compose config`（dbのパスワードと `SUI_DATABASE_URL` のパスワードが一致しているか）を確認します。次に、古い `sui_sensemaking_pgdata` のボリュームが残っていないかを確認します（`pg_isready` はパスワード認証を検証しないため、dbは正常に見えます）。詳しい復旧の手順は、installation.mdの同じ名前の項目を参照してください。 |
| AI提案が出ない | `SUI_LLM_PROVIDER`、プロバイダのエンドポイント、SafeMode |
| 書き出しが失敗する、または長時間終わらない | 対象文書のスキーマ、画面上の進捗と中止のメッセージ、ブラウザのコンソール |
| ワーカーが停止する | 入力データ、ワーカーのコンソール、該当ワーカーの単体テスト |

## ワーカーに関する確認

ワーカーが原因らしいときは、まず、入力データの大きさ、スキーマ、レビューの状態を確認します。

診断やレビューパックの書き出しが長く続くときは、処理の名前、進捗の表示、キャンセルできたか、キャンセルしたあとの画面のメッセージを記録します。キャンセルして復帰できるときは、入力データの大きさや対象の範囲を小さくして、再試行してください。キャンセルしても画面が復帰しないときは、ワーカーのエラーとして扱います。

レビュー差分の計算が長く続くときも、同じように扱います。比較対象の文書を読み込んだあとに「差分を計算中」と表示されるか、キャンセルしたあとに「差分計算を中止しました」と表示されるかを、記録します。差分の計算は、比較対象の大きさや関係線の数に影響されます。再試行するときは、小さい比較ファイルでも再現するかを確認してください。

## 大きな文書や低速な環境での確認

大きな文書や低速な環境では、処理にかかる時間より、利用者が次の判断をできる表示になっているかを確認します。

| 確認の対象 | 見ること | 記録すること |
| --- | --- | --- |
| 検索 | 検索語を入力しても、画面が固まって見えないか | 検索語、カードの数、結果が表示されるまでの体感 |
| 表示の切り替え | `表示` パネルが、画面の幅からはみ出さないか | 画面の幅、開いたパネル、見切れの有無 |
| 共有前確認 | `共有と再現` で、SafeMode、公開範囲、出力形式を読めるか | SafeModeの状態、公開範囲、実行する前に読めた警告 |
| 診断 | 実行中はボタンが無効になり、キャンセルできるか | 進捗の表示、キャンセルしたあとのメッセージ |
| レビューパックの書き出し | 処理中の表示とキャンセルが、同じ画面の中で分かるか | 出力の粒度、キャンセルできたか、成功か中止かの結果 |
| 差分の確認 | 比較対象を読み込んだあと、差分の計算中と中止の結果が分かるか | 比較ファイルの大きさ、キャンセルの操作、結果のメッセージ |

狭い画面で再現したときは、`390px`、`768px`、`960px`、`1440px` のうち、どの幅で確認したかを残してください。画面の外にはみ出した情報が、SafeMode、共有前確認、キャンセルの操作に関するものであれば、軽微な崩れではなく、共有と復帰の判断に関わる問題として扱います。

開発者がテストを実行するときは、次のようにします。

```bash
cd 03_Implement/frontend
npm run test
npm run typecheck
```

特定のワーカーのテストだけを実行するときは、そのファイルを指定します。

```bash
npm run test -- src/worker/<test-file>.test.ts
```

## 記録する情報

- 発生日時
- コミット
- URL
- ブラウザと画面の幅
- 操作の手順
- 期待した結果
- 実際の結果
- APIのステータスコード
- コンソールのエラー
- 再現率

秘密情報、APIキー、トークン、顧客の生のデータは記録しません。どの情報を残せるか迷うときは、[data_handling.md](data_handling.md) を確認してください。

## サポート診断バンドル

上のテンプレートを手で入力する代わりに、画面ヘッダーの「サポート診断バンドル」から、共有してよい情報だけを、その場で組み立てられます。

- 障害の分類（下の表の5つのコードのどれか。必須）を選び、必要なら直近のHTTPステータスを入力して、「診断バンドルを生成」を押します。
- 生成すると、必ず全文のプレビューが表示されます。コピーとダウンロード（`diag-bundle.v1` 形式のJSON）は、内容を確認したあとにだけ行えます。
- 自動では送信しません。生成、プレビュー、コピー、ダウンロードは、すべて手元での操作です。
- 含まれるのは、アプリのリビジョン（検証できないときは `unknown`）、正規化したブラウザのファミリーとメジャーバージョン、OSのファミリー、選んだ障害の分類、任意のHTTPステータス、SafeModeの状態、プロバイダの種類、対象の文書のversionとupdatedAt、カード、島、エッジの件数だけです。
- カード、島、ナラティブなどの本文、文書ID、エンティティのIDと参照、APIキー、トークン、パスワード、内部のURL、個人情報、UserAgentの生の値、エラーメッセージとスタックトレースは、SafeModeがONかOFFかにかかわらず、含まれません。
- パネルを閉じる（Escape、×、キャンセル）と、生成した内容はメモリから破棄されます。

## 障害の分類と一次切り分け

5分以内の一次切り分けは、次の分類コードで記録します。

| 分類コード | 判断の条件 | 最初に確認するコマンドと操作 |
| --- | --- | --- |
| WEB-ENTRY | 画面の表示の異常が主な症状 | ブラウザのコンソール、`docker compose logs web --tail=100` |
| API-UNAVAILABLE | APIが応答しない、502や503 | `curl -fsS http://localhost:8080/api/healthz`、`docker compose logs api --tail=200` |
| SAVE-FAILURE | 保存に失敗する、再読み込みで内容が合わない | ネットワークのステータス、`docker compose logs db --tail=100` |
| IMPORT-VALIDATION | インポートで、スキーマの検証に失敗する | インポートのエラーダイアログ、schemaVersion、検証の内容 |
| SHARE-SAFEMODE | 共有や書き出しの前の警告、マスクの警告 | 共有と再現パネルで、SafeModeと公開範囲を確認する |

## 診断の最小の手順

個人で運用するときは、役職の分担を設けず、Maintainerが診断と復旧を行えます。

1. 分類コードを1つ選び、5分以内の一次切り分けを行います。
2. 画面の症状、必要最小限のコマンドの結果、SafeModeの状態を確認します。
3. 解決しないときだけ、症状、再現率、秘密情報を除いたログ、未解決の点を残します。

秘密情報やマスクしていない本文の共有、SafeModeの緩和、元に戻せないデータの変更が必要になったときは、診断を止めて、[運用手順](operations.md)の安全確認に進みます。組織が職務の分離を求めるときは、組織の役割と承認の手順を、別に適用してください。

完了の条件が足りず、検証が済んだと判定できないときは、調査を完了とせず、[operations.md](operations.md) の暫定対応のメモとして、不足している点を記録して引き継ぎます。

## 手順を再現できることの確認

調査が終わったときに、次の3点を必ず残します。

1. 同じ症状を再現できる最小の手順（3〜7ステップ）。
2. 実行したコマンドと、その結果（成功か失敗か）。
3. 再試行するために必要な前提（環境変数、SafeModeの状態、対象の文書）。

## 復旧の基本

1. 変更の直後なら、直前の設定の差分を確認します。
2. DBへの接続やマイグレーションのエラーなら、backendのログを確認します。
3. frontendの表示だけがおかしいときは、キャッシュを無効にして再読み込みします。
4. LLMや監査ログのHTTP連携が関係するときは、いったん `SUI_LLM_PROVIDER=none` と `SUI_AUDIT_EXPORT_ENABLED=false` に戻して、もう一度確認します。

復旧を急ぐときも、秘密情報を含むログをそのまま共有しないでください。共有する前に、APIキー、トークン、個人情報、顧客の生のデータを取り除きます。
